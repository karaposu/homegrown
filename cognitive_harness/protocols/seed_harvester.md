> **Loading note.** This protocol is loaded at the START of a harvest dive — a `/traverse` run whose purpose is to extract seeds from a studied source. It is **used together with `/traverse`, never standalone**: the traverse pipeline (Articulate → Surfacing → Sensemaking → Decomposition → Innovation → Critique → Routelister → CONCLUDE) is the *engine*; this protocol defines *what the dive does with the source* and *what it must output*. Read it in full before the dive's first discipline runs; its steps ride the disciplines (the composition map below says which step lands where).

> **Naming.** Working name: **seed_harvester** (it harvests output-seeds from a source). Alias: **seed_generator** — the user's original coinage, which half-fits (the front step genuinely *generates*) but collides with this project's two *input*-senses of "seed" (the innovate discipline's trigger; the paradigm-sweeper's seed-block). Renaming is a one-move change if the alias is preferred.

# Seed Harvester — the harvest protocol

A protocol for extracting **seeds** from a studied source: generate candidate germs by crossing the source with the project context, gate them for informativeness and provenance, type them by what they do for you, grade them by whether to act or watch, and record them where they can be found and used later. **Enumerate, never select** — the protocol lists and records; choosing which seed to develop belongs to the human or the between-inquiry layer.

The harvest's success-measure is **seed-yield, not breakthrough-count**. A breakthrough (a new frame or practice) is simply a seed already grown — the rare top of a ladder whose reliable middle is the seed. Score the dive by what it planted, and keep the quality gate that makes each seed credible.

---

## 1. What a seed is

**A seed is a unique, usable, anchored, epistemically-live germ extracted from studying a source — harvested now, planted later.**

Its plain form: **what the material makes you think of, for your project — that, gated.**

Four properties, each load-bearing:

| Property | Meaning |
|---|---|
| **Usable** | It is harvested as a yield of study and later *used as input* — when someone develops a recorded seed, that seed becomes the trigger of its development run (same object, later stage). |
| **Anchored** | It names a concept in the project it relates to — a component, a design decision, an open question, a standing frame. The anchor is **constitutive**, not a label: it is one of the two inputs that *produce* the seed (see §2). A candidate that cannot name a real anchor is dropped. |
| **Gated** | It passed the two-door "is this news?" filter (§3). |
| **Deferred payoff** | Its value lands later, after development. This is what separates a seed from an *import* (which pays off now). Never develop a seed at harvest time — that collapses it into an import and spends the dive on what the lifecycle defers. |

**A seed is a hypothesis, not the thing itself.** Its natural form is *"maybe our X could be Y"* — explicitly speculative, uncommitted. A seed that would grow into a new paradigm is not that paradigm; it is the germ of one. Keep the record's wording in hypothesis form.

## 2. Where seeds come from — the crossing

Seeds are **generated, not found**. Extraction is a **generative crossing**, not a lookup:

- **Input 1 — the source claim:** a structure the material genuinely exhibits ("human memory comes in multiple types").
- **Input 2 — the project anchor:** a component, decision, or frame the project actually holds (our memory design).
- **The move:** carry the structure across (**transfer**), push past what the source says (**extrapolate**), or fuse it with a nearby project concept (**combine**).
- **Output — candidate germs, one-to-many:** project-directed hypotheses the source does not contain ("maybe our memory could be an ensemble of distinct components"; "maybe memory components could work async" — the source says nothing about the project; the crossing makes these).

Three rules govern the crossing:

1. **One-to-many is intrinsic.** Different moves applied to the same source claim yield different germs. Run the moves deliberately per major source claim; do not stop at the first candidate. **Run the crossing over an explicit coverage table — every major claim × every hot anchor: each cell either ATTEMPTED (a stated hypothesis-sentence, however weak) or SKIPPED with a stated reason ("cold anchor" / "same phenomenon as cell X" / "no genuine source-support possible"). The interesting candidates are often in cells a first pass would have skipped.**
2. **Generate first, gate after — never gate during.** The gate applied inside the generative step strangles the divergence that produces the interesting candidates. Two phases, strictly ordered.
3. **The moves are mechanism-kin of the innovate discipline (transfer/extrapolate/combine at micro-grain) — but this is NOT a nested innovate run.** No mechanism sweep, no development, no testing-toward-solutions at harvest time. The gate and the grades do the filtering; development happens later, in the seed's own run.

**Foreignness gradient:** the more foreign the source domain, the more of the extraction must be generated (a psychology paper contains nothing project-relevant to draw out — every candidate is made). Project-native sources sit toward the other end (some candidates are literally present in the text), but even there crossings run (one component's structure carried into another).

## 3. The gate — two doors, and what fails

A candidate passes the gate only if it is **news about a load-bearing thing** — it must change your epistemic state about something that matters, through either door:

- **The novelty door:** you learn something the project *doesn't yet have* — a missing component, a new mechanism, a new frame, a design option not yet held.
- **The confidence door** (bidirectional): you resolve a real, previously-open uncertainty about something the project *does* have — toward **sound** (confidence rises) or toward **flawed** (confidence falls).

What still fails, by name:

- **Decorative agreement** — affirming something you were already certain of. No uncertainty resolved, no news.
- **Decorative speculation** — the generation-side twin: idle "maybe X could be Y" that changes no future decision. Generation is cheap and one-to-many; this is the flood the gate exists to stop.
- **Unanchored candidates** — nothing real on the project side (the anchor-guard).
- **Fabricated transfers** — the **source-support** condition: the source must *genuinely exhibit* the structure being transferred. This is a **provenance** check, not a value check: a candidate failing it may still be a fine idea, but it is not a seed *of this source* — recording it as one falsifies the harvest's yield-claims and lends the candidate an evidential weight it does not have. Every recorded seed states its source-support. (Label the parts: a paper's STATIC per-problem tuning heuristic does not license an "online-adaptive" claim — the extrapolated form is OURS, and the record says so.)
- **No-decision candidates** — the changes-a-future-decision test: a seed must be spendable on a real future decision.

**Apply the gate in both directions.** Don't manufacture seeds to look productive (the gate is what makes a seed credible); don't wave off real ones to look strict (an affirmation of something genuinely uncertain is a real seed). And no property of the *source* other than its news-value raises a candidate's standing — not the source's fame, not how richly it confirms what we own, not how sharply it mirrors us, not how important its *target* is (leverage-of-target is a routing signal, never a grading signal).

**Prior folds govern at their sites.** A settled fold/kill from an earlier dive re-opens at a new site ONLY if all three hold: (a) the fold's premises name a different site, shown verbatim; (b) the new site's evidence postdates the old adjudication; (c) the candidate anchors in the new site specifically. Extending a fold beyond its stated premises to kill a fresh candidate is **fold-inflation** — the mirror-image of yield-inflation; both corrupt the record.

## 4. The types — what the seed does for you

Every gated seed is one of exactly three function-types — the three possible yields of a crossing:

| Type | When | Action it routes |
|---|---|---|
| **Inspiration** | the crossing creates a candidate for something the project *lacks* (absent → offered) | **ADD** — build/adopt it later. Sub-kinds (the development-actions): build · mechanism · frame · refine · connect |
| **Affirmation** | the crossing lands on a present thing and *raises* confidence in it (the confidence door clears) | **CONFIRM** — close the open question; spend the confidence (cite / green-light / stand down) |
| **Provocation** | the crossing lands on a present thing and *lowers* confidence in it (the confidence door fires) | **CHALLENGE** — re-open the settled question; raise an investigate-item |

Coverage holds by construction (absent/present is a true either-or; up/down exhausts the present branch; no-news is gate-excluded). Provocation is structurally required but was, at this protocol's writing, not yet exemplified in the harvest — watch for the first one rather than assuming the class is populated; a long emptiness is itself data.

## 5. The grades — act or watch

| Grade | Test | Action |
|---|---|---|
| **LIVE** | it clearly changes a future design decision | **act** — it is development-ready now |
| **NASCENT** | interesting, anchored, might mature — but doesn't clearly change a decision yet | **record and watch** — REQUIRES a **maturation-trigger** (a specific, checkable condition under which it is re-examined for promotion) |

A nascent seed without a maturation-trigger is a junk-drawer entry — the flood re-entering through the back door. The trigger is mandatory, not decorative.

## 6. The pipeline, and how it rides a /traverse dive

The protocol's abstract pipeline is **GENERATE → GATE → TYPE → GRADE → RECORD**. In a harvest dive it composes with the traverse disciplines like this:

| Protocol step | Where it lands in the dive | What happens there |
|---|---|---|
| *(setup)* | Articulate + `_branch.md` | the dive's purpose declares the source + this protocol; the project anchors in scope are named |
| **GENERATE** (the crossing) | Surfacing → Sensemaking → **Innovation** | Surfacing brings the source's claims AND the project anchors into view (both crossing-inputs) — **the source read FULLY by default; flagged-shallow only with named skips and straddle-awareness (never cut inside a section)**; Sensemaking stabilizes what the source actually claims (source-support's raw material) **and may flag likely-hot cells — it never closes the field; the crossing worklist IS the §2 coverage table, owned by Innovation**; **Innovation runs the deliberate crossing pass over the coverage table (skips carry reasons) — per major claim × hot anchor, the three moves, one-to-many, ungated; fresh sources run generator-weighted breadth by default (anything less is justified cell-by-cell); candidates are never singularized ("THE candidate") before the gate; the innovate discipline's own test cycle is delegated to the gate — no in-run development** |
| **GATE** | **Critique** | each candidate prosecuted both ways: which door, is it news, is the anchor real, does the source genuinely exhibit the transferred structure, does it change a future decision — SURVIVE/KILL per candidate; **after the first survivor, ask ONCE at field level: "what does this source offer that the table never contained?" (an empty answer is valid, stated — the anti-satisficing backstop)** |
| **TYPE + GRADE** | Critique → CONCLUDE | survivors typed (inspiration/affirmation/provocation → sub-kind if inspiration) and graded (live / nascent + trigger) |
| **RECORD** | **CONCLUDE** | the finding gets its `## Seeds` section; each seed is appended to the global index (§8) |

The routelister exhaust runs as usual; recorded seeds typically appear there as onward routes (a live seed's development is a natural route entry) — but the routelister enumerates, it does not develop them either.

## 7. The seed-record — the crossing, serialized

Each recorded seed preserves the crossing that made it: **the hypothesis (the output) plus both inputs as provenance.** This is what makes a seed auditable later — when a maturation-trigger fires, the re-examination's evidence is in the record.

```
seed:
  id:                <dive-shortname>-S<n>
  hypothesis:        "maybe our <X> could be <Y>" — the germ itself, in hypothesis form
  type:              inspiration | affirmation | provocation     (action: add | confirm | challenge)
  kind:              build | mechanism | frame | refine | connect   (inspiration only)
  anchor:            <the project concept — REQUIRED; the crossing's project-side input>
  source:            <the studied source>
  source-support:    <what in the material licensed it — REQUIRED; the crossing's source-side input>
  door:              novelty | confidence-up | confidence-down
  grade:             live | nascent
  maturation-trigger: <REQUIRED for nascent — specific and checkable>
  move:              transfer | extrapolate | combine              (telemetry; optional)
  confidence:        high | med | low
```

The record is **capped**: enough to develop from, never the development itself.

**Granularity: distinct anchor ⇒ distinct record.** Candidates sharing one mechanism across different anchors are SEPARATE records that cross-reference each other; merging sites into one record requires explicit in-record justification (why ONE development-action genuinely covers all sites). The merge stays allowed — the default flips to split.

## 8. The output contract — where seeds land

Two surfaces, one declaration + one accumulation:

1. **The finding's `## Seeds` section** (the per-dive declaration, human-readable). Every harvest dive's finding MUST carry it — including the explicit-empty form ("No seeds passed the gate this dive," with a one-line note of the strongest candidate that failed and why). Any *other* traverse finding MAY carry it when a dive incidentally yields a gated seed — the crossing is source-type-agnostic; seeds are not paper-exclusive. Each entry is the compact record of §7. The section is **additive**: it changes nothing else about the finding.

2. **The global index — `devdocs/seeds/_seed.md`** (the cross-dive accumulation, machine-findable). At CONCLUDE, append one line per recorded seed: `id | hypothesis (short) | type/kind | grade | anchor | dive-path | date`. Never delete entries; a seed that later proves dead is marked, not removed (loss-prevention is the index's whole point — seeds buried in prose get silently forgotten; the index is where the between-inquiry layer looks). Maturation-triggers are re-scanned here: when one fires, the seed's record in its finding is the re-examination's input.

Consumption story (what "use them later" means): a future development run picks a seed from the index, reads its full record in the finding, and starts a dive with the seed as its input trigger — the record's hypothesis + anchor + source-support are the dive's starting material. The record must therefore stand alone: a reader who has not seen the source can still tell what the germ is, what it is for, and what licensed it.

## 9. Failure modes

| # | Mode | Recognition | Corrective |
|---|---|---|---|
| 1 | **Lookup regression** | the dive only reports what the source says; candidates are quotes/paraphrases, none project-directed | re-run the crossing pass: per major claim, the three moves with the project anchors in view — the candidates worth having are *made*, not found |
| 2 | **Speculation spam** | many recorded "maybe X could be Y" entries that change no decision | the gate's decision-test + informativeness were under-applied; re-gate; check the nascent pile for trigger-less entries |
| 3 | **Fabricated transfer** | a record's source-support, on checking, is not actually in the source | provenance violation: the candidate is not a seed of this source — remove it from the yield (it may be re-recorded elsewhere as free ideation); re-check the dive's other records |
| 4 | **Premature development** | the dive develops a candidate (designs the solution, tests variants) at harvest time | the deferred-payoff property is being violated — cap the record, stop; development belongs to the seed's own later run |
| 5 | **Dumping-ground** | nascent seeds accumulate without maturation-triggers, or triggers never get re-scanned | the trigger requirement is mandatory; the index re-scan is where watching actually happens |
| 6 | **Yield-inflation** | seeds manufactured to make the dive look productive (warm sources, streak-relief after empty dives, grade-bleed from a rich predecessor) | the gate both ways; a NO-yield dive with an honest empty `## Seeds` section is a valid outcome, not a failure — and an ABOVE-band yield where every record is gate-clean is equally valid; never trim records to stay in-band |
| 7 | **Silent loss** | a real seed lives in the finding's prose but not in `## Seeds` / the index | the RECORD step is part of the protocol, not optional bookkeeping — CONCLUDE checks the section exists and the index was appended |
| 8 | **Pre-gate narrowing** | the crossing field was selected before the crossing ran (pre-picked worklists; "THE candidate" singularized upstream of generation; modes sized to one candidate on a fresh source); candidate-count ≈ survivor-count on a rich source | re-open generation with the §2 coverage table; the anti-manufacturing guard's home is the GATE and the RECORD — never generation (§2 rule 2) |

## 10. Telemetry + self-assessment

Report with the dive's `## Seeds` section (one line each): candidates generated / gated-in / killed-at-gate (with the dominant kill reason) · **coverage: cells attempted/possible (+ skip-reasons stated)** · **the field-level second-harvest question asked (answer may be "nothing")** · types (I/A/P counts) · grades (live/nascent) · doors · moves used. Self-assessment: **PROCEED** (crossing ran deliberately **over the coverage table**; gate applied both ways; records complete; index appended) / **FLAG** (any step skipped or any record incomplete — name it).

## 11. Usage

```
/traverse "harvest <source> for seeds — run the seed_harvester protocol
           (cognitive_harness/protocols/seed_harvester.md)"
```

The dive loads this protocol at start; the composition map (§6) places its steps; CONCLUDE produces the finding with `## Seeds` + appends the index. The protocol never runs outside a traverse dive. **Before framing, identity-check the source against already-graded sources (title/authors + a few distinctive-phrase counts): a duplicate re-routes the dive to a re-pass against the original's baseline instead of double-grading.**

**Folder naming (the class marker).** A harvest dive's inquiry folder carries the marker right after the timestamp:

```
devdocs/inquiries/<YYYY-MM-DD_HH-MM>__SEED_HARVEST__<source-slug>/
```

The marker makes harvest dives group visually in the flat inquiries list and greppable in one move (`ls devdocs/inquiries | grep SEED_HARVEST`); the `<source-slug>` names the *source* (not necessarily a paper — any studied material). Applies going forward; pre-marker dives keep their original names (their paths are already cited elsewhere).
