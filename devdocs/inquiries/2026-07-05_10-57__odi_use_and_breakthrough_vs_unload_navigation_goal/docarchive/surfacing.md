## PART A — Item 1: The Index's Uses (FACTs from the docs/findings)

- **U-1 — PULL: a worker, at the start of its already-assigned inquiry, enriches its chosen topic.** [core · FACT] ODI doc: Look-Up = *"the new traverse knows its topic… it queries the index: 'which open Direction labels relate to what I'm working on now?'"* What the result is used for — the 00-47 offer-menu: **absorb-while-warm** (do the surfaced direction now, cheaply, in-context) / **inform-the-finding** (note the open thread) / **mark-done** (record it handled). *"An offer, not an interrupt"* — declinable, so it can't derail the pass.

- **U-2 — EYES: the navigational session enumerates the index into the field the orchestrator selects over.** [core · FACT (finding-committed, not canon-committed — flagged below)] The 05-13 correction: *"make the open-directions index one of the inputs the eyes enumerate"*; the orchestrator then selects using traversal memory. The query result here = aging open directions entering the **enumerated field of directions** — the thing the steering canon says navigation exists to produce. Note honestly: the steering canon's input list has only a hook for this (*"future navigation memory or graph files"*); the commitment to feed the index to the eyes comes from the corrected findings, not canon text.

- **U-3 — DEDUP/LINK: filing-time housekeeping.** [peripheral · FACT] ODI doc: at File time, check the new direction against the index to avoid double-filing and to link related directions across traverses. *"Housekeeping, not the main use."*

- **U-4 — TELEMETRY: the index as measurement surface.** [supporting · FACT] ODI doc: *"it records what got set aside, what got revived, and what stayed open forever — revival rates, how long directions sit, which get picked up. Traversal memory is the project's missing measurement surface."* The query result here isn't a direction at all — it's *data about the traversal* (for the assess step).

- **U-5 — MARK-DONE: the state write-back.** [core · FACT] 00-47: the second write — *"recording that a direction has been handled… what turns the pile into a real memory of what's been done"* (canon's memory = visited/selected/**outcome**). Not a query result; the write the queries depend on to stay truthful.

- **U-6 — The traversal-memory placement (what the results ARE in design terms).** [core · FACT] ODI doc's two-faces passage: traversal memory = **selection record** (roads taken) + **option memory** (roads noticed-but-not-taken); the index is the option-memory face. So in traversal-memory terms: U-1's result = option-memory **spent into the current probe** (enrichment); U-2's result = option-memory **composed into the field for the decide step**; U-5 = option-memory **reconciled into state** (moving items toward the selection-record face: picked-up, with outcome). SUSTRALL's remember step (*"what was visited, selected, why, with what outcome"*) is served by the writes (File + mark-done), per 00-47's READ≠MEMORY.

**Item-1 shape [core]:** the uses are not scattered anymore — they sort into **two reads on two layers** (U-1 below the inquiry boundary; U-2 above it) **+ two writes** (File; U-5 mark-done) **+ two by-products** (U-3 housekeeping; U-4 telemetry). Every query result has a named consumer and a named traversal-memory role.

## PART B — Item 2: The Criterion's Ground (FACTs from the canons)

- **B-1 — The navigational session's LOAD, itemized by the steering canon.** [core · FACT] The canon gives the load in two parts. **(i) Warming** — *"Codebase orientation… Long-run trajectory (read inquiry folders' finding.md files)… Recent trajectory: scan recent inquiry folders by datetime prefix… Last-2-days trajectory: inspect the most recent inquiry folders and changed files… Target inquiry read."* Explicitly bounded: *"The warmed context should not be tried to be mapped. It is a context and time waste. Most that could be done is 3-stage warming (generic / technical / short-term-goal)."* **(ii) The job itself** — *"reads inquiry artifacts; maps movement-space; identifies candidate next moves; names blockers and gates; explains excluded directions; tracks selected moves and outcomes."* SUSTRALL: the session *"runs the enumerator (routelister) over a finished cycle or territory. It produces the typed field of directions."*

- **B-2 — What routelister-into-loop UNLOADED (the precedent the criterion points at).** [core · FACT + one inference] The steering canon describes the pre-move state: the navigation session *"runs /routeman against completed inquiry artifacts"* — i.e., the enumeration discipline ran **in the navigation session, cold, over finished artifacts**. The traverse loop now runs routelister as its exhaust step: every inquiry pre-enumerates its own onward field **while warm**, leaving `routelister.md` + `_route.md` in its root. 00-21's benchmark distillation (which survived its critique): the move *"(i) relocated a whole existing discipline into the loop at almost no new cost, and (ii) made every traverse contribute movement-space memory the steering layer can later consume."* [inference, grounded:] so what the navigation session no longer does is **per-inquiry enumeration from scratch** — its remaining enumeration job is *cross-inquiry*: compose the pre-enumerated per-inquiry fields over the territory and judge what matters now.

- **B-3 — The bootstrap direction (why "unload the navigation session" is the era-relevant criterion).** [core · FACT] SUSTRALL: *"automation lives below the inquiry boundary (six disciplines auto-chain within an inquiry); above it, every function is human — cross-inquiry traversal lives in the user's head."* So every mechanizable piece moved **below** the boundary shrinks the above-boundary function that must eventually be defined/built as the navigation session + orchestrator. The user's stated starting point ("add sth more to the traverse loop… which would unload the navigational session and make it easy for us to define and create it") is exactly this bootstrap move-class.

- **B-4 — Canon SILENCE on the navigation session's cost structure.** [core · FACT-of-absence] Neither canon itemizes *how much* of the navigation session's difficulty lies in which input — there is no cost breakdown of warming vs enumeration vs judgment. Consequence: any unload claim can be **structural** (a named input becomes a pre-built artifact) but not **quantitative** (no "X% of the load"). The honest ceiling on Item 2's verdict strength.

- **B-5 — The navigation session's remaining hard core, per canon.** [core · FACT] The failure mode the canon centers is *cold navigation* — *"reads the latest finding, understands the local words, but does not understand the project well enough to know what move matters."* Fresh whole-field **judgment** is the session's essence (SUSTRALL: "fresh perception each time"). No store can do the judging — the canon's design *forbids* it doing the choosing anyway ("Navigation sees; it does not choose"; selection = orchestrator).

## PART C — Item 2: The Unload-Mechanism Candidates (possibility-items, generated)

- **C-1 — PRE-ACCUMULATE: the index does the cross-traverse gathering incrementally, in-loop.** [core · inference grounded in B-1] Without the index, the eyes' option-field must be assembled at session start by sweeping recent inquiry folders' route-maps (`routelister.md`/`_route.md` per inquiry) — literally the canon's *"scan recent inquiry folders by datetime prefix"* warming input, done cold, every time, re-paid per session. With the index, each traverse appends its open directions at File time (warm, incremental), so the eyes open **one pre-built artifact** instead of performing a per-session sweep. The sweep work moves below the boundary and is paid once per traverse instead of once per navigation session.

- **C-2 — PRE-PRUNE: mark-done keeps the field truthful without re-derivation.** [core · inference grounded in U-5] Without mark-done, the eyes must re-derive which past directions are still open (cross-checking findings against route-maps — exactly the *"which directions were tried and wasted?"* question the steering canon lists). With mark-done written in-loop at handling time, open-vs-handled is **recorded state**, not a navigation-time investigation. The eyes read state; they don't reconstruct it.

- **C-3 — PRE-RESOLVE: pull retires some directions before they ever reach the eyes.** [supporting · inference grounded in U-1] Every absorbed-while-warm direction is handled inside a worker pass and mark-done'd — it never becomes above-boundary load at all. Smaller field → less to see, less to judge. (Honest bound: magnitude unknown — depends on the pull hit-rate, which 00-21 already flagged as unmeasured.)

- **C-4 — The PATTERN claim: the ODI is a second instance of the routelister-into-loop move-class.** [core · inference] The move-class: *relocate work from the navigation layer into the loop's warm exhaust, where it's cheap and incremental*. Routelister-into-loop relocated **per-inquiry enumeration**. The ODI relocates **cross-inquiry accumulation + state-keeping** (File + mark-done). Same direction of motion, same warm-session economics, next rung up (per-inquiry → cross-inquiry artifacts).

- **C-5 — THE COUNTER-CASE (surfaced with equal force).** [core · inference + FACTs]
  1. **Gathering is not seeing.** The index accumulates and records; it does not warm, judge relevance against the current project state, weight, or compose. The eyes' hard core (B-5: fresh whole-field judgment; avoiding cold navigation) is **untouched**. The index shrinks the *clerical* inputs, not the *cognitive* job.
  2. **Class difference from the precedent.** Routelister-into-loop relocated a **whole discipline** (the enumeration itself). The ODI relocates **bookkeeping around the discipline's outputs** (accumulation + state). Real, but a smaller class of move — 00-21's "adds a read step rather than relocating a discipline" verdict survives on this axis.
  3. **Warming is mostly untouched.** Of the canon's warming list (B-1), the index serves only the option-field slice of "recent trajectory / open directions." Codebase orientation, long-run trajectory, and target-inquiry reading remain fully on the eyes.
  4. **The unload claim is structural, not measured** (B-4): one named warming input becomes a pre-built artifact; no percentage can honestly be attached.
