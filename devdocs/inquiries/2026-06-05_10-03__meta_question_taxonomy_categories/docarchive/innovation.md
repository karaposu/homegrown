### P1 — Taxonomy Structure Bundle

**Piece question:** What is the structural shape of the taxonomy?

#### Principal candidate (elaborated taxonomy structure)

The meta-question taxonomy has **2 load-bearing axes**:

**Axis A: target-of-perception** — what kind of property the meta-question perceives about the task. The 3 primary types:

- **Structural** — perceives intrinsic properties of the task itself (its scope, its complexity-class, its time-horizon, etc.). The task is what it is; Structural meta-questions classify or characterize that.
- **Relational** — perceives task-to-project relations (context-need; kinds of external information that would be load-bearing; relational stance toward existing project state; preparation substrate for cross-discipline coordination).
- **Interpretive** — perceives task-to-user-intent (hidden meaning behind the surface ask; implicit acceptance criteria; unstated quality bar). Interpretive meta-questions infer what the user actually wants beyond what they said.

**Axis B: substrate-mode** — what evidence the meta-question requires to be answered:

- **Pre-context** — answerable from task statement + LLM general knowledge alone. No surfaced material needed.
- **Post-context** — requires surfaced material (e.g., output from `/surfacing`) to answer well. The pre-context version of the same perception would be hypothetical-relational at best (per the 21-12 finding's mode); the post-context version is concrete.

The 2 axes cross into a **6-cell grid**:

| Cell | Type × Mode | Cognitive operation | Population status |
|---|---|---|---|
| 1 | Structural × pre-context | classify intrinsic property | populated (MQ1) |
| 2 | Relational × pre-context | perceive-need + produce preparation substrate | populated (MQ2) |
| 3 | Interpretive × pre-context | infer hidden meaning | populated (MQ3) |
| 4 | Structural × post-context | Validate or Refine prior structural perception | currently empty |
| 5 | Relational × post-context | Validate or Refine prior relational perception | currently empty |
| 6 | Interpretive × post-context | Validate or Refine prior interpretive perception | currently empty |

**The 2 post-context cognitive operations:**

- **Validate** — check whether the pre-context perception (made in pass-1) still holds given surfaced material. Output: a verdict (binary or graded — held / partially-held / didn't-hold).
- **Refine** — produce a sharpened version of the pre-context perception using surfaced material as new evidence. Output: positive content (an updated perception, not just a verdict).

Cells 4-6 currently empty under task-define2's variant (a) commitment ("only Rephrase re-runs in pass-2"). Whether they get populated depends on variant-(a) tension resolution (see P3).

#### Piece-Level Inversion candidate

**Assumption being reversed:** 2-axis 3-types-×-2-modes-with-2-operations taxonomy.

**Reversal direction (a): 1-axis only** (target-of-perception, no substrate-mode). Tested at sensemaking Ambiguity 1; rejected because doesn't enable pass-1/pass-2 distinction (the user's stated downstream concern).

**Reversal direction (b): many-axis (5+ axes from surfacing AX4-AX8)**. Tested implicitly through axes-load-bearing analysis; rejected as over-specified.

**Reversal direction (c): different type names** (Classification/Preparation/Inference instead of Structural/Relational/Interpretive). Tested at sensemaking Ambiguity 2 + Load-bearing concept test on 5 names; rejected because names tied to operation/function are too narrow.

**Inversion-candidates generated, tested at sensemaking, rejected.** Compliant via reference to sensemaking work.

### P2 — Mapping + Applications Bundle

**Piece question:** How does the taxonomy apply — MQ mapping, rule (b) refinement, fuzziness resolution?

#### Principal candidate (elaborated mapping + applications)

The taxonomy applies to the existing 3 base MQs cleanly. Each MQ instantiates exactly one primary type in pre-context mode:

| MQ | Type × Mode | Cognitive operation | Downstream consumer |
|---|---|---|---|
| **MQ1 (scope)** | Structural × pre-context | Classify task's scope (time-horizon / conceptual / project / feature / cross-cutting / other) | MultiScope (within-Task-Define) |
| **MQ2 (context-need)** | Relational × pre-context | Perceive context-need (verdict ∈ {yes, no, uncertain}) + produce preparation substrate (kinds-plural + relational stance in hypothetical-relational mode) | Runner → /surfacing (cross-discipline) |
| **MQ3 (intent-vs-surface)** | Interpretive × pre-context | Infer underlying intent vs surface ask | Rephrase (within-Task-Define, direct) |

Mapping is clean: no boundary cases among the base 3. The taxonomy retroactively justifies WHY these 3 were the original base set — they cover the 3 primary types under the pre-context constraint, making the pre-context column structurally exhaustive on axis A.

**Bounded-extensibility rule (b) refinement.** Current rule (§2.3): "must constrain Rephrase." This rule was based on the implicit assumption that all MQs feed Rephrase as constraints, which is true at the architectural level but obscures the per-type primary downstream consumer.

Refined rule (b): **"must constrain some downstream operation"** — with per-category specifics:

- **Structural extensions** → constrain MultiScope (primary; via the scope-axis-feeding mechanism) + Rephrase (indirect via MQ-constrains-Rephrase general mechanism)
- **Relational extensions** → constrain runner → /surfacing (primary; via the preparation-substrate mechanism) + Rephrase (indirect, via pass-2 context-informed-refinement once it exists)
- **Interpretive extensions** → constrain Rephrase (primary, direct; via vocabulary shaping)
- **Post-context extensions** (Validate / Refine) → constrain pass-2 operations (currently Rephrase under variant a; potentially other ops under future variants)

Rules (a) "about task structure/framing" and (c) "one-sentence" preserved unchanged. Rule (a) covers all 3 primary types (intrinsic / relational / interpretive properties are all about task structure/framing). Rule (c) is authoring economy; applies uniformly.

**The taxonomy resolves the meta-question fuzziness at 3 dimensions:**

- **Category coverage** — meta-question = structural perception of one of 3 primary property types about the task, in one of 2 substrate modes. The category is exhaustive on axis A under the bounded-extensibility rule (a) constraint (extensions must be about task structure/framing → falls into intrinsic / relational / interpretive). Extensions that don't fit any type either (i) belong to a fundamentally new primary type (requires taxonomy revision via separate inquiry) or (ii) aren't meta-questions at all.

- **MQ heterogeneity** — the 3 base MQs are heterogeneous because they instantiate 3 different primary types. This is structurally correct, not a defect. Each MQ has distinct cognitive operation + distinct primary downstream consumer + distinct answer-shape, all explained by its type. The heterogeneity is a feature: it lets the 3 base MQs cover the 3 primary types with minimal redundancy.

- **Extension authoring** — proposed extensions classify into (a) primary type, (b) substrate mode, (c) cognitive operation per cell. The per-type rule (b) refinement provides authoring guidance: knowing the type tells the author which downstream operation the extension must constrain.
