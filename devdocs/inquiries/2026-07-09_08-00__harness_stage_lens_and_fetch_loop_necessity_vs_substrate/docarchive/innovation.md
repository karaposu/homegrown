## (1) ★ The crystallized axis (the division-of-labor design principle)

> **The cognitive harness should not re-implement what the Claude Code substrate already does well. The substrate owns raw *data-gathering* — re-reading files, re-grepping, re-searching until it has the bytes; that is its competence, and it is good at it. The harness should make explicit only the re-fetch *decisions* that are disciplined judgments worth recording — above all the re-anchoring judgment: "has the articulated aim moved to a materially different territory, such that I should re-surface?" Substrate owns data-gathering (competence); harness owns judgment-governed re-fetch (regulation + record).**

Grounding (kernel-bet §5, verbatim): *"competence is scale's domain… regulation + record is precision's domain… the verifiable commitment practice — criteria-files-before-data, declared deviations, versioned records."* The axis is that line applied at the granularity of a single re-fetch decision. (Combination: the canon line × the fetch question.)

The axis answers all three of the user's prompts at once — it *is* the finding's spine. What follows (the view, the gate, the emergent) are its projections.

## (2) ★ The design view (a legibility artifact — a VIEW, not a rename)

The user's pre/processing/post-processing lens, crystallized as a diagram the finding can carry. It is a **feedforward skeleton**; the fetch loops are its **cross-stage feedback edges** — which is exactly why naming the stages makes the fetch loops legible.

```
            PREPROCESSING            PROCESSING                 POSTPROCESSING
          ┌───────────────┐   ┌──────────────────────────┐   ┌──────────────────┐
   ──────▶│ articulate    │──▶│ sensemaking              │──▶│ critique         │──▶ (answer)
          │   ⇅  (fetch)   │   │  decompose               │   │ routelister      │
          │ surfacing     │   │  innovate                │   └────────┬─────────┘
          └───────▲───────┘   └───────────┬──────────────┘            │
                  │                       │                           │
                  │   (b) proc→pre        │                           │ (c) post→everything
                  └───────────────────────┘                           │   "loop again with
                    back-edge: sensemaking's                           │    a refined focus"
                    missing-material re-surface                        │   (the traverse
                    (the latent 2nd site)                              ▼    OUTER loop)
                                                       re-run the whole pipeline
```

Three back-edges, three grains:
- **(a) preprocessing-internal:** articulate ⇅ surfacing — the one WIRED fetch loop (pair grain).
- **(b) processing → preprocessing:** sensemaking → surfacing — the LATENT 2nd site (pair grain; missing-material only).
- **(c) postprocessing → everything:** critique → the whole-pipeline re-run — the traverse OUTER loop (pipeline grain; already built).

**The emergent this view makes visible:** an otherwise-feedforward pipeline has exactly these feedback edges, and *fetch loops are what those edges are*. (Lens-shift.) A view for legibility — not a proposal to rename the traverse-assembled skills (the user's own scoping).

## (3) ★ The criterion-as-seed-gate (the actionable output for `fixpt-S1`)

The 23-46 seed gated a "genuine site" on **wired-vs-latent** (has a second real caller been built?). This dive adds the missing **WHY** — *why does a site deserve an explicit loop at all?* — via the axis (absence-recognition: the prior gate answered "is it built?" but never "should it be?"):

> **A discipline-pair is a genuine explicit-fetch-loop site only if the re-fetch decision is a disciplined RE-FRAMING JUDGMENT — not mere data-gathering the substrate already owns.** The two gates compose: a site earns extraction when (judgment-governed) AND (a second such site is actually wired).

Applied (the blind test, as the gate's worked example):

| Candidate | Judgment-governed? | Verdict |
|---|---|---|
| articulate_warm ↔ surfacing | ✓ "has the aim moved to new territory?" | genuine (wired) |
| sensemaking → surfacing (missing-material) | ✓ "wrong model vs missing material?" | genuine (latent) |
| critique → more input | ✗ pipeline-grain; the outer loop already owns it | not a distinct site |
| innovation → more examples | ✗ internal re-generation, no upstream re-fetch | not a site |
| any step → read another file | ✗ pure data-gathering | substrate owns it |

**Status: record-for-later.** This sharpens the seed's gate; it builds nothing. (Constraint-manipulation: "don't build" turns the criterion into a gate refinement, not a construction.)

## (4) ★ The assembly emergent (run the assembly check) — sized honestly

Composing the axis across the whole harness, it **generalizes beyond fetch_loop** into a whole-harness design heuristic:

> **Make explicit (as a discipline/protocol, with a recorded criterion) only the decisions that are disciplined judgments; defer raw capability to the substrate.**

This answers, for *any* proposed harness feature, "should this be an explicit disciplined operation, or left to Claude Code?" — the same question the substrate-challenge (Item C) raised for fetch_loop.

**★ Honest sizing (anti-inflation — required):** this is **mostly a re-statement** of the kernel-bet's competence/regulation line (*"competence is scale's domain; regulation + record is precision's"*), lifted to **operation-granularity**. The only genuinely NEW part is the **operational gate** — the "is a disciplined judgment governing this decision?" test as a concrete yes/no you can apply to a candidate feature. So: a **useful design heuristic, grounded in canon — NOT a new thesis.** It earns a mention as "the axis generalizes, and here's the canon it rests on"; it does not earn a claim of discovery. (Extrapolation, deliberately capped.)

## (5) ★ The required inversion — retreat, or sharpening?

The finding can be read two ways:

- **Reading A — a retreat:** "I conceded the skill point (I was wrong), and I admitted the substrate challenge is real (maybe we don't need fetch_loop) — so the 23-46 position is crumbling."
- **Reading B — a sharpening (correct):** the two concessions make the position **more defensible, not less.** Conceding **packaging** (it's a skill/protocol, not a mysterious third thing) removes a wrong distinction. Conceding **data-gathering to the substrate** removes an over-broad claim ("fetch_loop is a special harness thing everywhere"). What remains is a **tight, principled position**: *explicit discipline exactly where a re-framing judgment governs the re-fetch — and nowhere else.* That is stronger than the un-conceded version, because it now has a **boundary** (the substrate does the rest) and a **reason** (the recorded judgment), rather than resting on "fetch loops are special."

**What follows from Reading B:** the 23-46 finding is **upgraded, not retreated from** — shape and timing stand, packaging is corrected, and a *new necessity-criterion* (the axis) is added that the prior finding lacked.

**★ Anti-sycophancy check (this must not become self-congratulation):** the honest core is that **the user's two pushbacks drove the sharpening.** The skill-packaging correction is theirs; the substrate-redundancy challenge is theirs; the axis is the harness's own kernel-bet answering the question they forced. The finding should credit the pushbacks, not frame the result as my clever synthesis. (Inversion, kept honest.)

**Land: CONCESSIONS-AS-SHARPENING** — the position is stronger *because* it concedes the two things it should, and the concessions are the user's contributions, not a retreat and not my invention.
