## Phase 2 — Adversarial Evaluation

### Candidate 1 — Soundness verdict (meaning-readiness precondition is real)
- **Prosecution:** status-quo-bias? "DEVELOP presupposes ready meaning" may just re-describe the existing A→Su→S→D→I→C pipeline and call it an insight — trivially true (everything presupposes understanding).
- **Defense:** the non-trivial part is *where* it bites — at the **ROUTE level**. A routelister `DEVELOP` route is a bare "build it" that carries **no** A→Su→S→D meaning-front-end; the loop would have provided one, but the *route abstraction drops it*. So firing a bare DEVELOP route on a meaning-unready target genuinely skips the meaning-building the loop would have done.
- **Collision / Verdict: SURVIVE — with precision caveat.** Not a new cognitive truth; the real point is that the *route* abstraction omits the meaning-front-end the *loop* supplies. State it that way.

### Candidate 2 — Classification: MTTP pattern, NOT a 10th verb (steelman the verb case)
- **Prosecution (strongest verb case):** call the whole thing **"teleological (develop, carefully)"** — the meaning-building is just internal — and it passes the single-kind test → it's a verb. The Guidance field already carries execution detail; "fixed" vocabularies still evolve; DEVELOP is itself already a mini-composition (build+test).
- **Defense (external anchor):** the spec defines an engagement-type as "**a verb for HOW to engage a concept**" — ONE move on ONE concept. Safe-develop's *defining content* is "decompose into **sub-concepts** and run **separate** meaning-loops on each" — multiple concepts, multiple loops = MTTP criterion #1 ("references ≥2 MVL loops") verbatim. Labeling it "teleological" to force it through the verb-test is exactly the category-error the single-kind test exists to catch — it only passes if you **hide its multi-loop body**.
- **Collision / Verdict: SURVIVE (not a new verb).** The steelman only survives by collapsing safe-develop to "develop carefully" and concealing the multi-loop mechanism. Note: the boundary is *where the body lives* — which the execution-mode reframe (candidate 3) resolves.

### Candidate 3 — Survivor A (execution-mode reframe): backdoor verb-redefinition?
- **Prosecution (the user-flagged RE-TEST):** "DEVELOP has two execution modes — direct and staged" **modifies the DEVELOP verb's definition** (it now carries a mode parameter). After saying "don't add a verb," the inquiry is *changing an existing verb's semantics* — arguably worse (it touches the closed vocab's meaning). Backdoor.
- **Defense:** distinguish (a) changing DEVELOP's *type-definition* (what makes a route a DEVELOP route — the spec's "develop a sketched concept toward an instance") from (b) recognizing the *executor* can stage the work when a precondition is unmet. (b) leaves the verb's definition untouched; it's the function-signature-unchanged / implementation-branches-on-input distinction.
- **Collision / Verdict: REFINE.** The prosecution lands: "execution-mode of DEVELOP" MUST be stated so it does **not** alter the DEVELOP engagement-type's spec-definition. Safe form: **DEVELOP's definition is unchanged; what's added is an *executor convention* (not part of the engagement-type vocabulary) — "when a DEVELOP route is meaning-unready, the executor stages it via the [MTTP pattern]."** Keep the insight; drop any wording that reads as editing the verb. *(Answers RE-TEST flag 1: the raw "two modes of DEVELOP" DID risk reading as a verb-semantics change; the refined wording — executor convention, not verb edit — does not.)*

### Candidate 4 — Survivor B (`Confidence` proxies meaning-readiness)
- **Prosecution (external anchor):** the spec defines `Confidence` as "a per-route descriptive tag of perceived salience / **formed-ness**" — of the **ROUTE**. Meaning-readiness is about the **TARGET concept's meaning-layer**. Different referents — and they **diverge**: the crowboy route #3 ("resolution-aware renderer + fold + schema mark") is **HIGH `Confidence`** ("critique's #1 survivor"… "HIGH · Confidence: HIGH") yet bundles substantial *meaning*. So a route can be high-Confidence AND meaning-heavy. `Confidence` ≠ meaning-readiness.
- **Defense:** they often *correlate* (a vague route is often meaning-unready); Confidence is a cheap first cut.
- **Collision / Verdict: REFINE (kills the "suffices" claim).** The structural point wins, with a concrete counter (crowboy #3: high-Confidence, meaning-heavy). **`Confidence` and meaning-readiness are DISTINCT axes that diverge** — Confidence is route-formed-ness, readiness is target-meaning-state. Downgrade B to: "they sometimes correlate, but meaning-readiness needs its OWN signal if it is to be reliable; do not conflate them." *(Answers RE-TEST flag 2: B was overclaimed — Confidence does not already cover it.)*

### Candidate 5 — Survivor C ("traverse recursed one level up")
- **Prosecution:** the across-loops version isn't *literally* A→Su→S→D→I→C; it's decompose→[traverse per sub-concept]→develop. The "recursion" is loose.
- **Defense:** as a *principle* (meaning-before-build is fractal — holds within a loop AND across loops), it's honest and illuminating.
- **Collision / Verdict: SURVIVE — as principle-level framing.** Keep it as "the meaning-before-build *discipline* recurses across scales," with the note that it's the principle, not the literal pipeline, that recurses.

### Candidate 6 — Worth naming at all vs just-good-practice
- **Prosecution (D4, the anti-bloat check):** the mechanism already exists; a competent executor would naturally decompose a big meaning-unready target. Naming it risks the spec-bloat the user has spent this week cutting ("one loop, don't proliferate"). Maybe: "yes it makes sense; it's just good practice; no new spec object."
- **Defense:** the user's specific, repeated evidence is that WITHOUT a name/trigger "the LLM just goes and develops" — the bare DEVELOP route actively invites charging ahead, and the crowboy big-DEVELOP routes show the failure recurs. The MTTP class is *explicitly* the home for "name the movements we keep needing."
- **Collision / Verdict: SURVIVE (minimal-naming).** The do-nothing option is the honest FLOOR; the user's recurrence evidence justifies the MINIMAL form — a named MTTP entry + a one-line executor trigger-convention, **no new verb, no new schema field.** State the floor explicitly (if even the one-line convention goes unused, fall back to just-good-practice). Respects the anti-bloat stance.

### Candidate 7 — Tier (candidate / Branch-and-Synthesize specialization)
- **Prosecution (external anchor):** the MTTP test requires "at least one empirical instance OR operational specification." Safe-develop has **zero run instances**; the crowboy routes are *un-executed examples*, not instances of the pattern being run. The specific decompose→meaning-traverse→develop shape has no operational-spec doc either.
- **Defense:** the *primitives* are operationally specified (decompose, branch_inquiry, traverse exist) → arguably "operational specification" → candidate.
- **Collision / Verdict: REFINE → research-frontier leaning candidate.** Honest tier: "named; composable from existing primitives; **zero run instances**" → **research-frontier**, promotable to candidate/admitted on the first actual run. Don't overclaim "candidate."
