# Finding: The seed, generalized — a two-door gate, a project-agnostic definition, and a function-first taxonomy

## Changes from Prior

**Prior path:** `devdocs/inquiries/2026-07-07_12-02__seed_generator_protocol_reframe_harvest_toward_seeds/finding.md` (the inquiry that first defined a "seed" for this project's paper-harvest).

**Revision trigger:** User correction. After reading the prior four-property definition of a "seed," the user pushed back on three of its four properties and proposed a new way to categorize seeds.

**What's preserved:** The *shape* of the prior definition — a seed is anchored to a project concept, passes a quality gate, and has a deferred payoff. The two grades (LIVE / NASCENT). The five development-kinds (build / mechanism / frame / refine / connect). The reframe that the harvest's goal is seed-yield, not breakthrough-count.

**What's changed:** Three of the four properties widen. "Output, not input" is dropped (a seed *is* usable as input). "Anchored to a *harness* concept" widens to "anchored to a concept in *whatever project* you're in." The gate — the single biggest change — widens from one door to two.

**What's new:** A **function axis** for typing seeds (what a seed *does for you* — inspiration or affirmation), which becomes the primary way to categorize them. The prior five development-kinds move underneath it.

**Migration:** The prior definition is not wrong — it is a *special case* of this one (the harness-specific, inspiration-only, one-door corner). Anything built on the prior definition still holds; it just now has a name as a special case. The one concrete migration: the `harvest-goal-is-seed-yield` project memory, which stated the gate as one door, is updated to the two-door form (see Inherited Commitments Re-test).

## Question

This project builds a **cognitive harness** — a set of thinking-disciplines (surfacing, sensemaking, critique, and so on) run one at a time over a question. Alongside it runs a **paper-harvest**: it reads academic papers and asks what each one delivers to the harness. A prior inquiry defined the harvest's central output — a **"seed"** — with four properties: it is an *output* (not an input), *anchored to a harness concept*, *gated* (it must connect to something the harness doesn't already own), and its *payoff is deferred*.

The user read that definition and corrected it, in five parts:
1. **Usable-as-input:** "seed is sth that can be used as input" — a seed's essence is that you can *use* it, which contradicts "output, not input."
2. **Content types:** "it can be idea or concept or analogy seed" — a seed's *content* can take several forms.
3. **Project-agnostic:** "sth unique that we can use in our project whatever the project is (not just this harness project)" — define a seed generally, not just for this harness.
4. **Affirmation-seeds:** on the gate — "kind of yes, but it can be a seed of affirmation too" — a seed that *confirms* something can be valid, which the prior gate (which required connecting to something *un-owned*) excluded.
5. **Function-kinds:** "different kinds of seed such as seed of affirmation, seed of inspiration etc, but that's later to determine" — seeds can be typed by what they do for you, with the full list deferred.

The goal: revise the definition honestly. This is a **Meaning-layer** inquiry — it settles what a seed *is*; it does not build the `seed_generator` protocol (that remains a sequenced follow-on, now consuming the corrected definition).

**The honest lead:** the user's corrections are right. Three of the four properties were genuinely too narrow, and — as it turned out — the prior definition even contradicted itself on one of them. What follows credits the corrections first, and then makes one careful hold: the gate should *widen*, not *disappear*.

## Finding Summary

- **The corrections are right; the prior definition was a special case.** The prior definition had the right *skeleton* (anchored + gated + a deferred payoff + a lifecycle) but drew each property too narrowly. Revising it means *generalizing* it, not replacing it — the prior definition is what this broader one looks like in the harness's own inspiration-only corner.

- **A seed, redefined:** a **unique, usable, anchored, epistemically-live germ extracted from studying a source — harvested now, planted later.** "Harvested now, planted later" is the core image: you *pull* a seed as the yield of study, and its value is realized when you *use* it in a future decision.

- **The one careful hold — the gate widens to two doors, it does not vanish.** The prior gate asked one question: does this connect to something the project doesn't yet have? That is the **novelty door**. The user's affirmation-seed points at a second door the prior gate was missing — the **confidence door**: does this resolve a real uncertainty about something the project *does* have? A seed passes through *either* door. What still does *not* pass is decorative agreement — affirming something you were already sure of. The gate becomes an **"is this news?" filter**: news about what you're missing, or news about whether what you have is sound.

- **Why exactly two doors, and why this isn't a face-saving dodge:** the two doors are the harness's *own* structure, verified in three independent places — (1) its quality architecture is explicitly two-part, "Regression Detection [and] Improvement detection," with regression named the primary concern; (2) its north star calls "absence-of-failure signals" first-class; and (3) the harvest's original quality test already had two clauses ("NAMES … OR RESOLVES a genuine confusion") — the prior seed-definition simply dropped the second one. So the second door was never invented here; it was *restored*.

- **Seeds type by function first.** The primary way to categorize a seed is by what it does for you: **inspiration** (it opens the novelty door — you learn something the project lacks) or **affirmation** (it opens the confidence door — you confirm something uncertain is sound). The prior five development-kinds (build / mechanism / frame / refine / connect) are the *sub-structure under inspiration* — they describe how you'd develop an inspiration-seed. An affirmation-seed barely has a development-action; you just spend the confidence it gives you.

- **The definition is now project-agnostic.** A seed relates to a concept in whatever project you're in; for this harness, that concept is a canon frame, an un-built component, or an open design question. The two grades (LIVE = act on it, NASCENT = watch it) survive unchanged.

- **A concrete consequence:** an earlier paper (paper 20) produced a "mirror" that the old one-door gate scored as grade-neutral — it named nothing new. Under the two-door gate it is a real **affirmation-seed**: it resolved a genuine uncertainty ("is the harness's typed-everything design sound?"). The revision makes gradeable what the old gate couldn't score.

## Finding

### Why this inquiry exists

The paper-harvest is as much a calibration exercise as a reading one: it keeps testing whether a strict quality bar can tell "this teaches us something" from "this merely agrees with us." The prior inquiry defined the harvest's output — the seed — and the user, reading that definition closely, found it too tight in three places and proposed a better way to categorize seeds. Getting the definition right *before* building the extraction protocol matters: a protocol built on a too-narrow definition would inherit the narrowness. So this inquiry revises the meaning; the protocol is the next step.

One stance governed the whole inquiry, and it is worth stating plainly because the risk here runs opposite to usual. Normally the danger in grading an idea is rubber-stamping it to be agreeable. Here the user is correcting *me* (the prior definition was mine), so the dominant danger is **caving** — dropping a load-bearing constraint just because the user pushed on it. The mirror danger is also real: **face-saving** — defending a property I should let go. The inquiry tried to do neither.

### 1. The frame: this is a generalization, not a replacement

Look at the prior definition's four properties as a skeleton. A seed is *anchored* (it names a concept it relates to), *gated* (it must clear a quality bar), and has a *deferred payoff* (its value comes later), and it sits in a *lifecycle* (it gets recorded, then later used). That skeleton is sound. What was too narrow was the *scope* of each property: the anchor was welded to this specific harness; the gate admitted only one kind of pass; the "output, not input" property mistook a naming decision for an essential trait.

So the honest move is to *widen each property* while keeping the skeleton — to generalize. The prior definition then becomes a **special case**: the harness-anchored, inspiration-only, one-door corner of a broader concept. This isn't a rescue of the prior work; it's the accurate description of what fixing an over-narrow definition looks like.

There is even independent evidence that the correction was warranted, not just a preference. The prior definition *contradicted itself*: it asserted a seed "is an output, not an input," and then, a few lines later, described a recorded seed *becoming an input* to a later development run. A definition whose own text undercuts one of its properties has a real gap — and the user's "usable as input" correction is exactly what closes it.

### 2. The gate — the deepest correction (and the one careful hold)

This is the center of the revision, so it gets the most room.

**The prior gate, and what the user saw.** The prior gate asked: does this connect to something the harness *does not already own*? That is a test for **novelty** — a seed had to point at something new. The user's objection: an **affirmation** — a confirmation that some existing design is sound — can also be a valuable seed, yet it names nothing new, so the prior gate rejected it. The user is right that affirmations can be valuable. The question is what to do about it.

**The tempting wrong answer: drop the gate.** The most literal reading of the correction is "the gate was wrong — a seed is any unique, usable thing you extract, affirmations included." This is the caving danger, and it fails — on the harness's own logic. The harness treats regression-detection (confirming nothing broke) as first-class precisely because a regression-check *carries information only when the thing checked could have been broken*. A check that confirms already-known-good code tells you nothing. By that same logic, an affirmation of something you were *already certain of* carries no information — it's decorative. Drop the gate entirely and the harvest fills with decorative agreement, drowning the *real* affirmation-seeds in noise. That is the exact failure the gate exists to prevent. So "drop it" doesn't honor the affirmation-seed; it buries it.

**The right answer: widen the gate to two doors.** A seed must change your *epistemic state about something that matters* — and there are exactly two ways for that to happen:
- **The novelty door** — you learn something the project *doesn't yet have* (a missing component, a new mechanism, a new lens). This is the old gate.
- **The confidence door** — you resolve a real, previously-open *uncertainty* about something the project *does have* (is this design sound? does it hold up?). This is the door the prior gate omitted, and it is exactly where the affirmation-seed lives.

Affirming something you were genuinely unsure about passes the confidence door. Affirming something you were already sure of does not — it's decorative, the thing the gate still rightly stops. The gate's essence shifts from a *novelty* filter to an **informativeness** filter — an "is this news?" test. Novelty is news about what you're missing; a resolved uncertainty is news about whether what you have is sound.

**Why this is a real correction and not a face-saving relabel.** Three checks:

First, it *demotes* my prior position. The old gate goes from being *the* gate to being *one door of two*, with the confidence door added as co-equal — arguably primary, since the harness names regression its main concern. A face-saving move would leave the old gate intact and wave the affirmation-seed away; this cuts the old gate in half.

Second, it is grounded in three independent places in the harness's *own* documents, each checked against the actual text rather than asserted:
- The harness's quality architecture states in plain words that quality assessment has "2 parts … Regression Detection [and] Improvement detection," and that "at the core right now we are concerned most about Regression Detection." Two parts, regression primary.
- The project's north star states that "absence-of-failure signals are first-class."
- The harvest's original quality test (the "import test" from which this gate descends) was *already* two-clause: a paper delivers if it "NAMES a thing the harness does but never put into words, **OR RESOLVES a genuine confusion**." The NAMES clause is the novelty door; the RESOLVES clause is the confidence door. The prior seed-definition kept only the NAMES clause ("connect to something the harness does not already own") and silently dropped RESOLVES.

That third point is the strongest: the two-door structure was never invented in this inquiry. It was **already present** in the harvest's own test and got under-inherited by the prior seed-definition. This revision *restores* a latent structure — which makes it more conservative than it first appears, not a bolt-on.

Third, two independent lines of reasoning reach the same two doors. Beyond the harness's own documents, a plain software-engineering analogy lands in the same place: a unit test that only ever passes — that covers code never at risk — is redundant and gets deleted; a test earns its keep by covering a path that *could* break. An affirmation-seed earns its keep the same way: by resolving an uncertainty that could have gone the other way. Different domain, same principle.

### 3. The revised properties

With the gate settled, the four properties in their generalized form:

**Usable — a seed is harvested now and planted later.** The prior "output, not an input" conflated two different things: the *direction it's extracted* (you harvest it — the harvest produces, it doesn't consume) and the *direction of its value* (you use it later — as an input to a future decision). Both are true at once; they don't conflict. The naming reason for "output" still holds (it distinguishes the harvest's seed from two other things this project calls a "seed," both of which are inputs), but the *essence* is usability. And usable-as-input does not collapse the seed into one of those input-seeds: a harvest-seed and the innovation-discipline's trigger-seed are the *same object at different lifecycle stages* (a harvested germ that, when later taken up, becomes the trigger of a development run) — distinct by stage, not competing concepts.

**Anchored — to a concept in whatever project you're in.** The prior "anchored to a harness concept" was right that a seed must relate to a real concept (this is the user's own "relate to our concepts" constraint), but it welded that to *this* harness. The general form: a seed anchors to a concept in whatever project you're working in. For this harness, that concept is a canon frame, an un-built component, or an open design question. The harness becomes the running example, not the definition's ceiling.

**Gated — through the two doors** (section 2).

**Deferred payoff — a seed is planted, not banked.** The prior definition separated a seed (pays off later) from a full *import* (pays off now). The affirmation-seed pressures this: doesn't an affirmation pay off the moment you read it? No — its payoff is the *future decision the confidence unblocks*, not the moment of reading. You *plant* the confidence and spend it later (to green-light a build, to stop second-guessing a design). Contrast a full import, which you *bank* and use in the current work immediately. The line is: spent-later is a seed (for both inspiration and affirmation); spent-now is an import. "Unique" (the user's word) folds in here too — it's the informativeness the gate tests for.

### 4. How seeds type — function first

The prior inquiry typed seeds by **development-action**: build, mechanism, frame, refine, connect. The user proposed a different axis — by **function**: what the seed *does for you* (affirmation, inspiration, and so on, with the full list deferred). These are not competing; they nest, and the function axis is the better top-level cut.

**Function is the spanning cut.** Two function-poles are forced by the two-door gate, so they are principled, not arbitrary labels:
- **Inspiration** — opens the novelty door (you learn something the project lacks).
- **Affirmation** — opens the confidence door (you confirm something uncertain is sound).

The full enumeration of functions beyond these two is deferred, exactly as the user asked ("later to determine"). Only these two are minted, because only these two fall directly out of the gate's two doors.

**Development-action re-homes underneath inspiration.** Here is the structural reason function comes first rather than development-action: the five development-kinds (build / mechanism / frame / refine / connect) describe how you'd *develop* a seed — and they only branch richly for *inspiration*-seeds. An affirmation-seed has almost no development-action; you just spend the confidence it gives you (cite it, green-light a decision, stand down from a planned rebuild). An axis that structures only one of the two function-poles cannot be the top-level cut. Function *spans* the whole space (both poles exist and differ); development-action covers only one pole. So function is the **spanning cut** — the axis that partitions the whole space — and development-action is the rich sub-structure under the inspiration pole. (This is a claim about *coverage*, not importance: for inspiration-seeds, the development-action is still where the real routing happens.)

**Content is a real but different kind of axis.** The user's "idea / concept / analogy" is a third axis — the seed's *content* or form. It is genuinely real (the user named it, and it describes what a seed *is*), but it is *descriptive*, not *routing*: knowing a seed is an analogy rather than a plain idea doesn't by itself change how you develop it (an analogy can serve either function). So content sits beside the two action-routing axes (function, development) as a distinct *kind* of axis — it describes form rather than routing action. It is not lesser; it is a different sort of thing, and it stays lightly held until more seeds show whether any content-type ever does route an action.

**The two grades survive unchanged.** LIVE (clearly changes a future decision → act on it) and NASCENT (interesting, anchored, might mature → record and watch, with a maturation-trigger) are orthogonal to all of this — a seed can be, e.g., an affirmation-function LIVE-grade seed. The grades say *act or watch*; the function says *what it does for you*.

### 5. A consequence worth seeing

The revision retroactively makes something gradeable that the old gate couldn't score. An earlier dive (paper 20) produced what was then called a "mirror" — the harness's own typed-everything design philosophy reflected back in an unrelated research paper. Under the old one-door gate, that mirror was grade-neutral: it named nothing new, so it didn't pass. Under the two-door gate it is a real **affirmation-seed** — it resolved a genuine uncertainty ("is the typed-everything design actually sound, or should it be rebuilt?") by showing the same structure works elsewhere. The value is decision-relevant: *don't rebuild it*. The old gate had no way to score that; the two-door gate does. (Paper 20 is not re-run here — this is noted as a confirmation of the generalization, not a re-grading exercise.)

## Reasoning

**Why generalize rather than replace, and why the gate widened rather than dropped.** Two inversions were run at full strength and both were defeated:

- *"Drop the gate — the user is simply right that a seed is any usable extract."* Defeated on the harness's own logic: a regression-check on already-known-good code yields no information, so an affirmation of the already-certain is decorative — dropping the gate would let decorative agreement flood in and drown the real affirmation-seeds. The user's valid insight (affirmations can be seeds) is met by *opening a second door*, not by removing the doorframe.

- *"Development-action is the real taxonomy; calling function primary over-builds a deferred axis."* Defeated on coverage: development-action branches richly only for inspiration-seeds and degenerates to one action for affirmation-seeds, so it can't be the spanning cut. Function spans both poles and is canon-forced (the two doors), so it is the top-level axis — while the enumeration beyond the two poles stays deferred, honoring the user.

**Two file-checks did real work** (evidence the verdict wasn't a rubber-stamp). First, the claim that the harvest's quality test was "improvement-only and needs a regression-half added" was checked against the actual wording *before* being asserted — and found wrong in a productive way: the test already said "NAMES … OR RESOLVES a genuine confusion," so the second door was already there and had merely been dropped by the prior seed-definition. That turned a would-be new-invention claim into a more-conservative "restores a latent structure" claim. Second, the prior definition's self-inconsistency (output-not-input vs. the lifecycle-link) was confirmed in its own text, giving the usable-as-input correction independent structural support rather than resting on user preference alone.

**What was refined, not killed.** The critique corrected two of my own framings — in both directions. It caught an *over-claim*: "function is primary" was sharpened to "function is the spanning cut" (it covers the whole space), dropping the implicit and unsupported claim that function is *more important* than development-action. And it caught an *under-build*: I had demoted the user's content axis (idea / concept / analogy) to "provisional / weak" — which was deflation, grading down the user's own real distinction to look disciplined. Content was restored to a real *descriptive* axis, distinct in kind from the two routing axes. The same honesty guard thus bit in both directions within a single review — against caving to the user at the gate, and against over-correcting the user at the content axis.

**Anti-proliferation held three times.** The gate was kept to two doors (candidate third doors — "re-weight priorities," "reveal a connection" — were shown to fold into the two, and were flagged rather than minted). The affirmation-seed's development-action was kept to one (four candidate actions all reduced to "spend the confidence"). Content was kept as one descriptive axis rather than split. Each resistance applied the project's own decision-vs-label test (mint a category only when it changes an action).
