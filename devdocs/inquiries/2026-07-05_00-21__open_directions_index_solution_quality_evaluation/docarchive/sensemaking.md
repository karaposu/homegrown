## SV1 — Baseline Understanding

The ODI is a decent, cheap idea for progressing traversal memory, but probably not a breakthrough like the routelister-into-loop move; scaling might bite. (Initial impression, pre-analysis.)

## Phase 1 — Cognitive Anchor Extraction

**Constraints:**
- C1 — the benchmark ("breakthrough as routelister addition") has *specific* criteria (surfacing D5): protect/create a real cognitive organ; relocate an *existing* capability cheaply/intrinsically; ~zero new infra; reduce complexity elsewhere; enable a downstream capability (multihead).
- C2 — self-authored design; external anchors mandatory (paradigm sweep; push finding; the actual routelister-into-loop precedent; the empirical ~hundreds of write-only parked directions).

**Key Insights:**
- K1 — the ODI is an instance of F4 (entity-threaded registry); `_route.md` is F4's exemplar → not novel.
- K2 — the ODI is TWO separable halves: WRITE (File → an index) and READ (Look-Up → a topic-pull).
- K3 — the ODI is pull-only; a high-value parked direction nobody queries stays buried.
- K4 (emergent, load-bearing) — **push (U8) over parked directions PRESUPPOSES the index**: a watcher's CHECK greps recorded state, so "surface aging high-Essentiality directions uninvited" needs the directions recorded in one queryable place = the index. So pull and push are two READ strategies over the *same* write-half.

**Structural Points:**
- S1 — write half rides routelister's existing Direction output (F4 filing); read half adds a new front-of-traverse step.
- S2 — the existing committed traversal-memory design is F2+F3+F5; the ODI adds F4.

**Foundational Principles:**
- P1 — novelty ≠ value (a well-applied known pattern can be the right cheap increment).
- P2 — "good" must be scored per named axis (novelty / elegance / buildability / scalability / fit), not as one blob.

**Meaning-Nodes:** breakthrough-benchmark; pull-vs-push; the index as substrate; write-only-recreated; enrichment-vs-selection.

### SV2 — Anchor-Informed Understanding

The question is not "is the ODI good/bad" but "score this F4-instance on named axes against a specific benchmark." The design cleaves into a write half (index) and a read half (pull), and the sharpest emergent (K4) is that the index is a *substrate* that both pull and push read over — which means the ODI's real contribution and its committed read-strategy are different things that must be graded separately.

*(Meta-inspection H4/H5: concept names "index / pull / push / enrichment-vs-selection" match the corpus vocabulary (paradigm sweep families; U8); motivating examples are the real ~hundreds of write-only directions + the actual routelister precedent — not a toy set. Clean.)*

## Phase 2 — Perspective Checking

- **Technical:** the index is F4 (a queryable per-Direction store). Pull = query-by-topic at read. Push = a watcher grepping the store on a moment (U8). Both are reads over the same store. Technically, the store is the load-bearing artifact; the read strategy is swappable.
- **Human/User:** the user *already suspects* over-valuation ("is it really that good") and volunteers elegance + scaling doubts — they want the honest read, not reassurance. Under-selling their doubt would be the sycophantic failure.
- **Strategic/Long-term:** the canon's hard problem is *steering* (deciding what to do next across inquiries). Enrichment-of-a-chosen-heading (pull) is the easy half; selection (push, surfacing the high-value aging direction uninvited) is the hard half. The strategic prize is the hard half.
- **Risk/Failure:** the ODI's failure mode is a low harvest rate — the index grows monotonically (write-mostly) while pull only reads what a traverse happens to query. This *recreates the write-only problem one level up*, unless a read strategy actively harvests (push does; pull doesn't).
- **Resource/Feasibility:** the write half is nearly free (rides existing output). The read half (pull) is a new step of uncertain scaling. Push is also buildable here (U8: check+moment+interrupt, no daemon).
- **Definitional/Internal-consistency:** the ODI doc claims it "feeds the steering layer." Internal tension: pull needs a *current focus* to query with, so it enriches a heading already chosen — it cannot *originate* the selection. The doc's steering claim over-reaches its mechanism.
- **Self-Reference (H8):** evaluating a harness design with harness disciplines — external anchors in play (empirical write-only count; the paradigm sweep; the independent push finding; the real precedent). Not circular. ✓

### SV3 — Multi-Perspective Understanding

Major reframe: the load-bearing object is **the index (write half)**, not the pull. The index is the substrate both pull and push read over (K4). The ODI-as-written welds the foundational index to the *weaker* read strategy (pull) and then overclaims steering. So the honest evaluation splits three ways: (a) the index — foundational, cheap, real; (b) pull — fine for enrichment, weak for selection; (c) push — the higher-value read for the hard job, and it *needs* the index. This is a sharper structure than SV1's "cheap-but-not-breakthrough."

## Phase 3 — Ambiguity Collapse

### Ambiguity 1 — Is the ODI a breakthrough "as the routelister addition"?
**Strongest counter (steelman "YES, it is"):** the cheap-on-ramp is a genuine, strong virtue — it closes a real write-only gap using data that already exists; the first traversal-memory artifact is nearly free. That is exactly the kind of "relocate an existing capability cheaply" virtue that made the routelister move good.
**Why the counter fails (structural grounds):** the routelister-into-loop move (i) relocated a *whole existing discipline* into the loop and (ii) *enabled a new downstream capability* (multihead coordination via per-traverse route-maps). The ODI's cheap virtue is real but applies to the *write half only*; its read half is new-and-unproven, and the packaged design (index + pull-only) does not itself unlock a new capability — it enriches individual traverses. Meeting *some* benchmark criteria (cheap, rides-existing) on *one half* is not meeting them at the whole-design level. **Confidence: HIGH.**
**Resolution:** NOT a breakthrough as-packaged. The write half shares the routelister-addition's virtues; the whole design does not rise to that bar.
**Now fixed:** breakthrough-verdict = NO (whole-design); the benchmark criteria are the yardstick.
**No longer allowed:** grading the ODI "breakthrough" on the strength of the cheap on-ramp alone.

### Ambiguity 2 — Is the ODI *dominated* as the next step (deprioritize for push/distillation)?
**Strongest counter (steelman "YES, it's weak — drop it"):** pull's harvest rate may be low (write-mostly index), so it half-recreates the write-only problem; push (U8) surfaces the high-value directions uninvited and does the hard job; distillation (F6) handles scale. So maybe build push/F6 and skip the ODI.
**Why the counter fails (structural grounds):** push-over-parked-directions *presupposes the index* (K4) — a watcher's CHECK greps recorded state, so it needs the directions recorded in one queryable place, which is precisely the ODI's write half. The index is the shared substrate for BOTH reads. So the ODI is not dominated/skippable — its **write half is a prerequisite for the very alternative (push) that would "dominate" it.** What IS dominated is the ODI's *pull-only packaging*, not the index. **Confidence: HIGH.**
**Resolution:** the index (write half) is foundational and NOT skippable; the pull-only read is the weaker strategy and should not be the design's identity. Build the index; add pull AND push as reads (push likely higher-value for selection).
**Now fixed:** the index = the load-bearing contribution; pull = one read; push = another, over the same index.
**No longer allowed:** treating "the ODI" as identical to "pull," or treating the index as skippable.
**Model change:** the biggest one — from "ODI = the pull/enrichment half" to "the INDEX is the foundation; pull and push are two reads over it, and the doc welds the foundation to the weaker read."

### Ambiguity 3 — Novelty vs value (does F4-instance mean "not good"?)
**Strongest counter:** it's a known pattern (F4), so it's unremarkable.
**Why it fails (structural):** novelty and value are orthogonal (P1). The write half being a clean, well-chosen application of F4 is *why* it's cheap and sound — the known-ness is a virtue (proven pattern), not a demerit. F4-instance lowers the *novelty* score; it does not lower the *value* score. **Confidence: HIGH.**
**Resolution:** commit the split — novelty LOW; value of the index HIGH; value of pull-only MODERATE (enrichment) / LOW (selection).

### Ambiguity 4 — Scaling: fatal, non-issue, or addressable?
**Strongest counter (either extreme):** "fatal — the index grows unbounded and the read degrades" / "non-issue — LLMs read a lot."
**Why both fail (structural):** not fatal — F6 (distilled cascade) + Priority/Essentiality pruning are known, composable fixes, and push-reads grep rather than read-the-whole-pile. Not a non-issue — as-specced there is no distillation or pruning, and a fuzzy read over a monotonic write-mostly pile does degrade. **Confidence: HIGH.**
**Resolution:** scaling is REAL, NAMED, and ADDRESSABLE — unsolved as-specced, solvable by composition. A design gap, not a fatal flaw.

### SV4 — Clarified Understanding
The ODI decomposes into an index (foundational, cheap, F4, enables pull+push+multihead-steering), a pull read (fine for enrichment, weak for selection, the doc's committed identity), and named gaps (no distillation/pruning; pull-only under-harvests; the steering claim over-reaches). Not a breakthrough as-packaged; not weak/skippable either — it contains a foundational piece mis-packaged with the weaker read.

## Phase 4 — Degrees-of-Freedom Reduction

**Fixed:** breakthrough=NO (as-packaged); index=foundational & prerequisite-for-push; pull=enrichment-grade read; scaling=real-but-solvable; novelty LOW / index-value HIGH.
**Eliminated:** "it's a breakthrough"; "it's weak/skippable"; "the index and pull are one inseparable thing"; "scaling is fatal / non-issue".
**Viable remaining (for downstream, not this evaluation to decide):** build order — index first, then which read(s) and in what order (pull for enrichment, push for selection); whether to fold distillation in early.

### SV5 — Constrained Understanding
The solution space collapses to: **grade the index and the read separately.** The index is a genuinely good cheap foundational move (shares several routelister-addition virtues, enables the push it's "threatened" by). The pull read is a sound-but-modest enrichment mechanism that the doc over-identifies the whole design with and over-claims for steering. Scaling is a solvable design gap. The verdict is a *decomposed* grade, not a single number.

## Phase 5 — Conceptual Stabilization

### SV6 — Stabilized Model

**The honest verdict: a good, cheap, foundational piece — mis-packaged and slightly over-claimed — not a breakthrough.**

1. **Breakthrough? No — as packaged.** Measured against what made the routelister-into-loop move good (relocate a whole existing capability cheaply + unlock a new downstream capability), the ODI meets the "cheap, rides-existing" criteria on its *write half only*, and does not itself unlock a new capability. It's a good increment, not a breakthrough.

2. **Novelty low, value real — kept separate.** It's an F4 instance (`_route.md` is F4's exemplar), so nothing new as a paradigm. But the write half is a clean, proven application of F4 — the known-ness is *why* it's cheap and sound.

3. **The real contribution is the INDEX, not the pull.** The load-bearing insight: the index (record parked Directions in one queryable place) is the foundation, and both read strategies — pull (look-up) and push (a U8 watcher) — read over it. Push *presupposes* the index. So the index is foundational and not skippable; the ODI's pull-only packaging welds that foundation to the *weaker* read and under-sells it.

4. **Pull is the enrichment half, not the steering half.** Pull surfaces a parked direction only when a new traverse already heads toward its topic — it enriches an already-chosen heading; it cannot *originate* the selection ("what should I work on next?"). The doc's "feeds the steering layer" claim over-reaches its mechanism. The hard steering job belongs to push — over the same index.

5. **Scaling: real, named, solvable.** The monotonic write-mostly index + fuzzy full-pile read do degrade; there's no distillation or pruning as-specced. F6 (distilled cascade) + Priority/Essentiality pruning + push's grep-not-read-all are the composable fixes. A design gap, not a fatal flaw.

**Grade:** GOOD FOUNDATION, MIS-PACKAGED. The index is a genuinely valuable, cheap, foundational move (on the path, shares several breakthrough-virtues); the pull-only read is sound-but-modest and over-identified with the whole; not a breakthrough on the routelister-into-loop level; scaling is a solvable gap. **Highest-value correction for downstream: re-frame the design around the index as the substrate, present pull and push as two reads over it, and let push (the harder, higher-value steering read) onto the same foundation — rather than shipping index-welded-to-pull-only.**

**Delta SV1→SV6:** SV1 said "decent, not a breakthrough, scaling might bite." SV6 keeps "not a breakthrough / scaling real" but adds the load-bearing restructure: the index is a foundational substrate the doc under-sells by welding it to the weaker (pull) read, while the higher-value read (push) both needs that index and does the hard job the ODI over-claims. That restructure is the inquiry's real yield.
