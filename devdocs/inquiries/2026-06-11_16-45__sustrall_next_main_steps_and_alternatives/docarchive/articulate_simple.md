## Item 1 — the SUSTRALL next-steps roadmap with per-step alternatives

**Item text:** What are the next MAIN steps for achieving SUSTRALL, and — per step — what alternatives exist for now?

### MQ1 — verdict-axis (what kind of ask)

**Answer — identified-ambiguities-list:**
- **plan-the-path:** sequence the next main steps from the current state (post-Pipeline-Architecture, post-aMVLwr) toward the era-goal.
- **enumerate-alternatives-per-step:** for each step, the real, currently-available alternative ways to do it (with trade-offs) — the user's standing field-before-choice instinct applied to the build itself.
- **prioritize:** "next MAIN steps" implies main-vs-secondary — a priority/criticality judgment, possibly a single "do this first."
- **consolidate-the-worklist (implicit):** a standing worklist exists (`devdocs/next_steps_for_sustrall.md`); this session moved fast (new architecture, new runner) — the ask may include refreshing/superseding it.

### MQ2 — context-need axis

**Answer — identified-ambiguities-list:**
- **verdict (which context):** the SUSTRALL canon (the era-goal + its acceptance — explfine; the autonomy ladder; the Allocation Rule); `devdocs/next_steps_for_sustrall.md` (the standing worklist — must be READ, it may be stale vs this session); the Pipeline Architecture finding (the D1→D4→D3 growth path + its COULD/DEFERRED items — the freshest step-source); the Expedition finding (Turn 1; the pre-registration MUST whose window closes at the first turn-record; N≥20; the shakedown); the Turn Architecture finding (the turn-record as the Level-1 build item); the `/aMVLwr` runner (just built — changes what a "loop with exhaust" costs); the enduring-edge/coverage findings (the strategic frame the steps serve).
- **kinds:** a staged roadmap + per-step alternative-sets with trade-offs + a priority rationale + a worklist reconciliation.
- **stance:** synthesizer (consolidate the session's findings into one path), honest about which choices are the user's seat (naming, D4 adoption) vs assistant-executable, and about what's genuinely open vs settled.

### MQ3 — intent-axis (WHAT; action-endpoint shape)

**Answer — identified-ambiguities-list:**
- **endpoint-the-roadmap:** an ordered set of next MAIN steps (likely 3–6), each with what-it-is / why-it's-next / what-it-unblocks.
- **endpoint-the-alternatives:** per step, the currently-available alternatives (real options, not strawmen), each with its trade-off and when-you'd-pick-it.
- **endpoint-the-first-move:** possibly a single critical-path pointer ("if you do one thing next, do X").
- **endpoint-the-worklist-reconciliation:** how the answer relates to `devdocs/next_steps_for_sustrall.md` (confirm / supersede / update-proposal).

### MQ4 — boundary-axis (exclusions)

**Answer — identified-ambiguities-list:**
- **"for now":** alternatives must be currently available (today's tools, today's findings) — no speculative-future options.
- **"MAIN steps":** not the exhaustive worklist — the load-bearing few; secondary items only as context.
- *(Implicit)* **don't re-litigate the just-settled architecture:** the Pipeline finding settled the design two turns ago; steps should BUILD ON it. Alternatives may include genuinely-open choices (e.g., which mode for Turn 1) but not re-opening every committed decision.
- *(Implicit)* **execution is out of scope:** this is the plan + options, not performing the steps (Turn 1 itself, the D4 file creation, etc. remain the user's go).

### MQA — alignment across MQ1–MQ4

**RECONCILE:** plan-the-path folds with prioritize (an ordered MAIN-steps list IS a priority claim); enumerate-alternatives folds with the field-before-choice motive.
**SURFACE — irreducible opennesses (carried):** (a) does the user want the worklist FILE updated, or just the answer (the reconciliation endpoint's strength); (b) how many steps count as "main" (3? 6?); (c) whether "alternatives" includes do-nothing/defer options or only active variants.
Remaining: ALIGNED (the roadmap-with-alternatives shape governs).
