## Finding

### Context the reader needs

This finding operates inside an ongoing chain of refinements to a single cognitive discipline called **articulate_simple** — a five-operation discipline (Itemize / Meta-question / Deconstruct / MultiDepth / Rephrase) that takes a compact task statement and expands it into a per-item bundle the rest of the project's cognitive loop can work with. The discipline-explainer document for articulate_simple lives at `devdocs/how_articulate_simple_should_be.md` and is referenced throughout this finding by section number (§1, §2.4, §2.5, etc.). The discipline is committed to **substrate-bounded operation** per §1 of the doc — it does not fetch project files, read recent inquiry history, or load specific artifacts. The substrate is the task statement plus the LLM's general knowledge plus any session context already loaded.

The 21-52 finding (which this finding refines specifically on the MultiDepth dimension) established a **substrate-bounded chain**: substrate-bounded ⇒ any commitment the LLM makes about properties of the task is a guess (no project context to ground it on) ⇒ downstream consumers (other operations in articulate-simple's flow + the runner formulating input for the next discipline /surfacing + the user reading the framing to verify it) treat the guess as actionable ⇒ downstream operations propagate the guess as if it were grounded. The 21-52 verdict applied that chain to Meta-question commitments and narrowed Meta-question's permissive-answer range from four shapes (identified-ambiguity / confident commitment / hedged commitment / explicit-empty) to two shapes (identified-ambiguity / explicit-empty).

The 21-52 finding flagged **MultiDepth's purpose-wrapped output** as Cascade 1 — the same critique should apply, but the specific resolution was deferred to a follow-up inquiry per the cascade-acknowledgment-without-pre-decision meta-pattern (which says: name structural cascades honestly; defer their specific resolutions to follow-up inquiries with their own scope). This finding is that follow-up inquiry.

The user's request, verbatim: *"based on devdocs/inquiries/2026-06-06_21-52__no_commitments_pre_surfacing_safety/finding.md u said [the Cascade 1 prose quote about MultiDepth's purpose-wrapped suffering the same critique] lets dive deeper into this one."*

### What MultiDepth currently emits (background)

Under the current §2.4 of the discipline-explainer document, MultiDepth emits exactly two outputs per item:

- **Literal** — the task at its narrowest accurate framing. What is being asked, expressed precisely, with no purpose wrapping.
- **Purpose-wrapped** — the literal task INCLUDED in its perceived purpose chain. The text contains the literal task verbatim or near-verbatim, then chains its perceived purposes via causal connectives ("in order to" / "so we can" / equivalents).

Example from §2.4 (warm-context case for the input "improve auth module" with session context indicating a recent token-validation bug discussion):
- Literal: *"fix the token validation bug discussed"*
- Purpose-wrapped: *"fix login bug due to token validation in order to enable login feature for users, so we can login and test other features"*

The §2.4 INCLUDES-with-accuracy rule (load-bearing) requires purpose-wrapped to preserve the literal task verbatim; the rule prevents drift to a different task. §2.4 also commits MultiDepth to substrate-compliance — the purpose chain is inferred from the task statement + general knowledge (cold context) or session context (warm context); MultiDepth does not fetch from the project. The substrate boundary, in the doc's own words, "is the same as elsewhere in articulate."

This last commitment — that MultiDepth's substrate is the same as the rest of articulate-simple — is the structural ground that makes the substrate-bounded chain transfer cleanly. We'll return to it.

### The user is structurally right

The substrate-bounded chain from the 21-52 finding extends to MultiDepth's purpose-wrapped output symmetrically. The reasoning is structurally tight:

The substrate is identical. §2.4's substrate-compliance paragraph says explicitly: "MultiDepth does not fetch from the project. The substrate boundary is the same as elsewhere in articulate." When the LLM emits a purpose-wrapped output at the articulate-simple stage, it has no project context. The perceived purpose chain is necessarily a guess derived from the task statement + general knowledge + any session context.

Downstream consumers act on the guess. Rephrase (specified in §2.5 of the doc as varying "within the perceived scope, context-need, intent, and coherence" from Meta-question answers) reads MultiDepth's output as input — §1.1 of the doc commits "Deconstruct and MultiDepth's outputs are additional structure to vary along." The user reads the framing to verify it. Whichever consumers act on the purpose-wrapped output treat the LLM's perceived purpose chain as actionable framing.

This is contamination. A pre-context guess propagates through downstream framing as if it were grounded. Whatever the LLM perceived in cold context — "to improve readability" for a rename, "to enable login feature" for a token-validation fix — becomes the framing downstream operates within.

### Why the structural-property differences don't exempt MultiDepth

MultiDepth has five structural properties that differ from Meta-question commitments. Each is real; none reaches the contamination layer. We tested them one by one (this is the work Sensemaking did at Phase 2 perspective-checking + Phase 3 ambiguity-collapse).

**The INCLUDES-with-accuracy rule** anchors purpose-wrapped to literal verbatim. The rule prevents drift to a different task — purpose-wrapped can't morph "fix the token validation bug" into "redesign the OAuth flow." But the rule operates at the intra-MultiDepth integrity layer (drift between tasks); it does not prevent the perceived purpose chain from being wrong on the same task. Wrong-purpose-on-correct-task contamination is still possible.

**The literal output as fallback.** Downstream consumers have access to the literal output as a kind of ground truth — if they distrust purpose-wrapped, they can fall back to literal. This is a real structural mitigation that Meta-question commitments lack. But the default reading is still purpose-wrapped; consumers don't have a protocol that tells them to discount purpose-wrapped under cold context. The bias remains in the default reading.

**The perceivability principle.** §2.4 commits MultiDepth to not pad — it emits depth proportional to perceivable depth. This is substrate-honest behavior about DEPTH (how many connectives the chain has). It says nothing about CORRECTNESS (what the perceived purpose IS). A shallow chain in cold context can be substrate-honest about depth and still be a wrong guess about purpose.

**The rendering-vs-committing axis.** §2.4 says MultiDepth "renders depth of meaning." One could argue "rendering" is different in kind from "committing" — that rendering is making visible what's there rather than adjudicating what the answer is. The argument fails in cold context: rendering a perceived purpose chain IS committing to a perceived purpose chain when there's no project context to perceive against. The verb-distinction holds when there's substrate to perceive; it collapses when there isn't.

**The PATH-vs-ENDPOINT axis from MQ3.** The 22-44 finding distinguished MultiDepth from MQ3 (Meta-question 3, which infers user intent) on the basis that MultiDepth emits a PATH (literal + chain) while MQ3 emits an ENDPOINT (single statement of perceived intent). This distinction keeps the two operations from collapsing into each other. But it doesn't address substrate-bounded contamination; both PATH-form and ENDPOINT-form can carry guesses.

None of these five properties reaches the layer where the substrate-bounded chain operates. The chain runs: substrate-bounded ⇒ guess ⇒ downstream-bias-as-actionable ⇒ contamination. The properties operate at different layers: INCLUDES at intra-bundle integrity; literal-fallback at consumer-recovery; perceivability at depth-bound; rendering-vs-committing at verb-meaning; PATH-vs-ENDPOINT at form-shape. The 21-52 finding's K2 scope-mismatch crux explains exactly this: PERMISSION-style mitigations operate at the LLM-emission scope (authorizing hedged output), while contamination operates at the consumer scope (the consumer acts on whatever they receive). The layers don't connect. The same structural pattern applies here: MultiDepth's structural-property defenses operate at scopes that don't reach the contamination concern.

### The runner-bias claim from 21-52 is non-fatal but should be honest

The 21-52 finding's Cascade 1 prose said: *"Downstream consumers (the runner reading the purpose-wrapped to bias /surfacing toward the perceived purpose; the user reading the framing to verify it) act on the guessed purpose."* This named two downstream consumers: the runner (formulating input for the /surfacing discipline) and the user (verifying the framing).

But the runner-bias claim is not grounded in current §12 of the discipline-explainer document. §12's one-paragraph summary of articulate-simple says, in part: "The runner reads the Meta-question's MQ2 + MQ4 entries (preparation substrate + exclusions) and uses them to formulate the project's /surfacing discipline's input." Purpose-wrapped is not listed as a runner read.

This means the 21-52 Cascade 1 prose runner-bias claim may be speculative pending §12 clarification. Two interpretations are possible: either §12 is incomplete and the runner does in fact use purpose-wrapped (in which case the runner-bias claim is correct and §12 needs amendment), or §12 is correct and the runner-bias claim was a speculative addition in the 21-52 prose (in which case the runner-bias claim should be flagged speculative and the contamination case should rest on the confirmed downstream consumers).

The contamination case is robust either way. Rephrase is a confirmed consumer (per §1.1 of the doc). The user is a confirmed consumer (the user reads the per-item bundle). Two confirmed consumers are sufficient grounding for the contamination case.

### The verdict — REFINE-only-purpose-wrapped

Under the verdict, MultiDepth at articulate-simple stage emits per item:

- **Literal** — the task at its narrowest accurate framing. **Unchanged from current §2.4.** Literal preserves the input verbatim or near-verbatim; it carries no commitment to a perceived property of the task; per the new LITERAL-AS-NON-CONTAMINATING-OUTPUT structural insight (below), literal is structurally non-contaminating.

- **Purpose-ambiguity** — narrowed to a 2-shape range:
  1. **Identified-purpose-ambiguities** — when the LLM perceives openness about why the task is being requested. The output names the plausible purposes the task statement (plus general knowledge, plus session context) is consistent with, without committing to one. Example: for "Refactor the authentication module" under cold context, *"Purpose-motivation ambiguity: refactor could be for security hardening, for adding new auth methods, for cleaning up technical debt, or for migration to a different auth provider. Without project context, multiple purposes are plausible."*
  2. **Explicit-empty** — when no purpose-ambiguity is perceivable along the WHY axis. Example: for "rename foo to bar" with no session goals visible, the output is *"No specific purpose-ambiguity perceivable from the task statement at cold context"* (consistent with the 18-21 finding's empty-as-content principle: when ambiguity is not perceivable, emit explicit-empty rather than fabricate).

The slot for MultiDepth's second output is preserved (the 00-47 finding's Fixed-2 schema stays at 2 outputs per item). The content shape of that slot changes from commitment to identification.

The §2.4 INCLUDES-with-accuracy rule preserves its scope at the literal output. The rule no longer applies to the second output — identified-purpose-ambiguities lists plausible purposes rather than including the literal task verbatim in a wrapped chain. The rule's load-bearing role (preventing drift to a different task) is preserved for the literal half of the bundle.

The §2.4 substrate-compliance paragraph is preserved unchanged. The substrate boundary stays the same: no project-fetch; session-context allowed.

### Why this verdict is surgical — the LITERAL-AS-NON-CONTAMINATING-OUTPUT insight

A blanket refinement might have narrowed both literal and purpose-wrapped. We didn't, because of a structural insight that emerged in the analysis:

Within a multi-output bundle from an upstream substrate-bounded discipline, an output that preserves the input verbatim (or at its narrowest accurate framing) carries no commitment beyond the preservation itself — the LLM hasn't added any perceived content; it has just expressed the input in a clean form. There's nothing to contaminate. The contamination concern only applies to outputs that ADD perceived content based on the LLM's guess.

For MultiDepth, the literal output is input-preservation; the purpose-wrapped output was additive-content. Only the additive output needs to narrow. Literal stays unchanged.

This is the **LITERAL-AS-NON-CONTAMINATING-OUTPUT** insight. It applies broadly to multi-output bundles from upstream substrate-bounded disciplines — anywhere an upstream discipline emits both an input-preservation output and an additive-content output, the same surgical refinement pattern can be considered. The pattern's precondition is load-bearing: it applies **when the literal output is genuine input-preservation, not a curated paraphrase that secretly commits to a perceived framing.** When the precondition holds, the pattern enables surgical refinement; when it doesn't, the literal output may itself be contaminating and the analysis must extend to it.

Confirming evidence from neighboring domains was already in hand from the 21-52 finding's cross-domain validation work: compilers distinguish PARSE (syntactic identification of structure, no semantic commitment) from SEMANTIC ANALYSIS (commitment to meaning, after grammar binding completes). Parsers preserve input structure as an AST without committing meaning; semantic analyzers commit meaning post-binding. The structural distinction matches.

### Why MultiDepth's identity is preserved under refinement — the AMBIGUITY-NATURE distinction

Under refinement, both MultiDepth (via identified-purpose-ambiguities) and MQ3 (via identified-intent-ambiguities per the 21-52 narrowing) become ambiguity-identification operations. A real concern arises: do they collapse into the same operation?

The 22-44 finding distinguished MultiDepth from MQ3 via the PATH-vs-ENDPOINT axis — MultiDepth emits a PATH (literal + chain); MQ3 emits an ENDPOINT (single statement of perceived intent). Under refinement, MultiDepth no longer emits a PATH; it emits a list of plausible purposes. MQ3 no longer emits an ENDPOINT; it emits a list of plausible intents. The PATH-vs-ENDPOINT distinction loses its surface form.

But the distinction shifts to a different structural axis — the **AMBIGUITY-NATURE distinction**. MultiDepth identifies purpose-motivation ambiguities — the WHY axis (why the user wants the task done; motivation chain). MQ3 identifies intent-action ambiguities — the WHAT axis (what the user is trying to accomplish; action endpoint). These are genuinely different ambiguity dimensions even when the surface words overlap:

For "Refactor the authentication module" in cold context:
- MQ3-refined identifies intent-action ambiguities: "Is this iterate-on-existing or greenfield-rebuild?" (different actions)
- MultiDepth-refined identifies purpose-motivation ambiguities: "Is this for security hardening / for adding new auth methods / for cleaning up tech debt?" (different motivations)

In software-engineering vocabulary, "purpose" commonly maps to motivation/why (cf. "what's the purpose of this code") and "intent" to user-goal/what (cf. "what does the user intend to accomplish"). The distinction is clean in technical engineering vocabulary, though sometimes fuzzy in colloquial use — which is why this finding flags it for monitoring (Open Questions section below).

The operation-name "MultiDepth" is preserved on structural grounds. Under refinement, MultiDepth still renders something at a depth axis — it renders the openness of the purpose-motivation axis as identified ambiguity-richness in internal text (the carrier mechanism the 00-47 finding committed, now applied to ambiguity-richness rather than connective count). The user has the final call on the name per the 19-06 finding's asymmetric-naming-implies-output-identity meta-pattern (which was preserved at the 20-29 finding with the user-has-final-call note).
