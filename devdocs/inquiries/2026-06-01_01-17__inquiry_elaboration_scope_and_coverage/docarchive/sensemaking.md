## Phase 1 — Cognitive Anchor Extraction

**Constraints**
- **C1 — Identity is settled, scope is open.** 22-30 fixed "IE IS a discipline" with the arc comprehend → perceive request-structure → verify → elaborated-inquiry spec. This run sets *remit only* (meaning layer); re-arguing discipline-hood or designing spec sections is out.

**Key insights**
- **K1 (the spine) — request vs problem.** Everything in-scope operates on the **request / inquiry-framing**; everything that operates on the **problem's content** (model it, partition it into solution pieces, generate or judge solutions) is the loop (S/D/I/C) and is out. This is surfacing's frontier F1, promoted to the organizing anchor.
- **K2 — Upstream-first.** `discipline_taxonomy.md` places IE as Upstream, *before surfacing*, because it produces the framing whose *purpose* surfacing then consumes. So IE's "achieve" is the artifact the whole pipeline starts from.
- **K3 — rule-placement says the branch.md audits migrate in.** `discipline_rule_placement.md` ("smallest scope that contains what it governs") + the "pregnant meaning" diagnostic: the accreted branch.md checks (Step 3 comprehension, Step 3.5 transcription-fidelity, Step 3.6 reference-authority) are governed by the request-comprehension operation → their home is IE. branch.md thins to encoding/orchestration.
- **K4 — three jobs, object = the request.** 20-08's mapping holds but the object is the *request*, not the problem: comprehend-the-request (Comprehending on input), perceive-request-structure (one vs N inquiries + order), verify-framing-fidelity (a fidelity gate).

**Structural points**
- The output IS the boundary marker: an **elaborated-inquiry spec** (a loop-ready framing) + a **request-structure verdict** (single / N-parallel / N-sequential). If IE produced a *problem model* or *solution candidates*, it would have crossed into S/I.
- Neighbors fixing the borders: surfacing (draws items), sense-making (structures the problem), decompose (partitions the problem), innovate (generates candidates), td-critique (judges candidates), runner + `branch_inquiry` (encodes, spawns, gates).

**Foundational principles**
- **P1 — verb-on-object individuates.** IE's object is the request/inquiry-framing; each neighbor's object is the problem/territory/candidates. Same verb on a different object is a different discipline-phase, not territory theft (13-31's "one operation, N consumers").
- **P2 — meaning before structure** (Layer Commitment): set remit now; spec shape later.

**Meaning-nodes:** *task-definition elaboration* (raw request → loop-ready framing); *request vs problem*; *elaborated-inquiry spec*.

## Phase 3 — Ambiguity Collapse

**A1 — Does "cover task-definition elaboration" include forming a first-pass understanding of the PROBLEM?**
- *Strongest counter:* a good inquiry framing arguably needs some problem understanding, so IE should do sensemaking-lite.
- *Why it fails (structural):* problem-understanding is sense-making's verb on the problem; IE doing it duplicates work and erodes the discipline 13-31/05-24 explicitly preserved. IE needs only enough comprehension of the *request* to frame it; the problem model is produced downstream, by sense-making, on the framing IE emits.
- *Confidence:* HIGH. *Resolution:* IE covers the REQUEST framing; problem understanding is OUT (sense-making's). *Now fixed:* IE's comprehension depth = "enough to frame faithfully," not "a stable problem model."

**A2 — Is "perceive request-structure / split bundled requests" just `/decompose`?**
- *Strongest counter:* decompose could be pointed at the request.
- *Why it fails:* `/decompose` requires a *understood problem* (sensemaking is its prerequisite) and produces a coupling map + interfaces + dependency order over problem-parts. The request-split produces "there are N distinct inquiries, in this order" — shallower, request-level, no interface-mapping.
- *Confidence:* MED-HIGH (residual: the tailored-phase-vs-wrapper line, F3). *Resolution:* request-structure perception is IN (as a tailored phase); running `/decompose` on the problem is OUT.

**A3 — Is IE's "verify" just running `/td-critique`?**
- *Strongest counter:* the fidelity gate is "evaluate a candidate against criteria," which is td-critique's verb.
- *Why it partially holds / resolves:* it is that *kind* of move, but the *object* is the framing-vs-intent, not solution candidates; it's a single fidelity gate, not a fitness landscape. So a *tailored verify phase* is IN; invoking `/td-critique` on solutions is OUT.
- *Confidence:* MED (residual F2 — whether the gate needs a genuinely-new check). *Now fixed:* verify's object = framing fidelity (three axes), not solution quality.

**A4 — Does IE spawn the sub-inquiries / create folders / gate branch-creation?**
- *Strongest counter:* IE's output reshapes the pipeline, so it looks like it's driving it.
- *Why it fails:* perception/action split — IE *perceives and emits* the request-structure verdict + fidelity verdict; the *runner* (and `branch_inquiry`) spawns, encodes, and gates. A discipline whose output informs pipeline-shaping is still a discipline (routelister precedent).
- *Confidence:* HIGH. *Resolution:* spawning / folder-creation / gating / encoding-into-`_branch.md` are OUT (runner).

**A5 — Which of branch.md's current sections migrate INTO IE vs stay with the runner?** *(the "cover" boundary in practice — residual F4)*
- *Resolution principle (meaning-layer):* the **comprehension + fidelity** parts migrate in (5-meta-aspect question shaping; Source-Input preservation; Scope-Check as request-vs-goal fidelity; Step 3.5 transcription audit; Step 3.6 reference-authority audit). The exact line is a structural-layer detail; at the meaning layer the rule is **"comprehension + fidelity IN; orchestration OUT."** *Load-bearing-concept test (H4/H9):* the name "task-definition elaboration" = exactly this migrated bundle, and it matches the user's language ("task definition elaboration"). ✓

## Phase 5 — Conceptual Stabilization

*Accommodation check:* the model stopped needing revision after the frame-exit pass; perspectives now confirm rather than destabilize → stable, not premature.

### SV6 — Stabilized model

**Inquiry Elaboration's remit, at the meaning layer, is organized by one boundary — it operates on the REQUEST, never on the PROBLEM, and it perceives rather than acts.**

**ACHIEVE (purpose / characteristic output).** Turn a raw, possibly-imperfect request into a **loop-ready, fidelity-verified inquiry framing** — the *elaborated-inquiry spec* — plus a **request-structure verdict** (one inquiry / N parallel / N sequential, with order), so the loop never spends a full pass on a *misframed* or *wrongly-bundled* query. Success = the framing faithfully matches the comprehended intent and the bundle is correctly resolved.

**COVER (in-scope), as three coupled tailored phases, object = the request:**
1. **Comprehend the request, multilayer** — read past imperfect phrasing to the real intent; produce the framing's content (the 5 meta-aspects: subject / action / level / observation-targets / deliverable-shape). Depth = "enough to frame faithfully," not a problem model.
2. **Perceive request-structure** — is this one inquiry or several; parallel or sequential; in what order. (Request-level perception, not problem-decomposition.)
3. **Verify framing-fidelity** — does the produced framing faithfully match the comprehended intent, across the three axes from 04-00: internal consistency, faithfulness to user input (incl. transcription), and external validity of cited references. (Migrates branch.md Steps 3.5 + 3.6 in.)

**NOT COVER (NOT-list / borders):**
1. **Understanding / stabilizing the problem** → `/sense-making` (object = problem, not request).
2. **Partitioning the problem into solution pieces with interfaces + dependency order** → `/decompose` (IE only splits the *request* into sub-inquiries).
3. **Drawing items from a territory** → `/surfacing`.
4. **Generating solution candidates** → `/innovate`; **judging solution candidates** → `/td-critique` (IE's verify is *framing*-fidelity, not solution quality).
5. **Spawning inquiries / creating folders / gating branch-creation / encoding the framing into `_branch.md`** → the runner + `branch_inquiry` (perception/action split; IE emits the verdicts, the runner acts).
6. **Meta-routing the inquiry** — deciding the cognitive layer (Layer Commitment) or driving conclusion (Synthesis Trigger → CONCLUDE) → runner-meta, not IE.
7. *(05-24 NOT-list, re-tested and kept as explicit borders):* not converging to one stable model (that's #1), not relevance-tagging items (that's #3), not generating novelty (that's #4).

**How it differs from SV1:** SV1 had the right instinct ("comprehend the request, don't solve the problem") but no boundary principle and no border-list. SV6 gives the **request-vs-problem** organizing line, the **fidelity-as-headline** anchor (from the user's actual pain), the **upper bound** (compose-don't-fuse → tailored phases, not a mini-runner), and a 7-entry NOT-list with each border attributed to a specific neighbor or to the runner.
