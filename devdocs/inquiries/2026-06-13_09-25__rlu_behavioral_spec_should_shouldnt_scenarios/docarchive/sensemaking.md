# Sensemaking — rlu behavioral contract

## SV1 — Baseline Understanding

rlu is a small skill that records which enumerated routes got run and what they produced. The prior findings adopted it and settled where it writes (`_route_engagements.md`). This inquiry wants a deeper behavioral spec: a list of what it should do, what it shouldn't do, and what it must do in particular situations. Initial read: assemble the obligations + the NOT-list + a scenario table.

## Phase 1 — Cognitive Anchor Extraction

**Constraints (limits / requirements):**
- C1 — Must honor the settled write-target: per-inquiry `_route_engagements.md`, append-only, at the inquiry root.
- C2 — Must never mutate the route-map (`routelister.md`, archived/regenerated) or write process-state into `_route.md` (only the ↗ manifestation pointer is legal).
- C3 — Must reconcile with the adopted mechanism (two moments `start`/`done`, degraded `done`-without-`start`, `park`/`list`, the sweep, the graded window guard).
- C4 — Object-B (the project Selector-queue) is out of scope (deferred); rlu must not pre-empt it.

**Key Insights (non-obvious):**
- K1 — **The NOT-list is not a flat list of taboos; it is corollaries of ONE principle: rlu must never become a second decision-maker.** Don't-choose, don't-launch, don't-judge-content, don't-maintain-a-forward-queue all reduce to "decision-authority stays single (the human/Selector); rlu only records what already happened and points at it." (This is the loop-runner finding's "bright line" — never open the artifacts to judge — applied to rlu.)
- K2 — **The scenario set is not closed; it is generated by a few axes.** The named scenarios (informal run, forgotten start, crash, cross-inquiry, first-run, parked…) are *points* in a small axis-space, not an enumerable list. Specifying the axes covers scenarios we never explicitly named.
- K3 — **"should be / shouldn't be / scenarios" maps cleanly onto three structural faces:** should = the lifecycle transitions + invariants; shouldn't = the single-decider scope fence; scenarios = the generative axes that produce the situations. The user's tripartition is the spec's table of contents.
- K4 — **rlu's behaviors derive from three independent pillars, not one** — so the design is multi-anchored, not one idea with trim.

**Structural Points (components / relationships):**
- SP1 — Three pillars: **P1 single-decider** (→ the NOT-list), **P2 source-of-truth integrity** (→ append-only, never-mutate, truth-lives-locally), **P3 mechanize-or-it-won't-happen** (→ immediate start-row, sweep, degraded done, auto-metadata; grounded in the zero-for-109 lesson).
- SP2 — A state-machine over the route-engagement lifecycle: none → in-flight → done; plus parked; plus superseded.
- SP3 — Generative scenario-axes (the meaning-node for "in what scenarios"): A1 was-there-a-start · A2 who-ran-it (formal loop vs informal session) · A3 where-it-ran (same vs cross-inquiry) · A4 first-in-project? · A5 close-reason (done/parked/superseded/abandoned) · A6 cardinality/concurrency (single/multi/parallel) · A7 route-level (inquiry vs project/Navigator).
- SP4 — Two write-targets, both legal: `_route_engagements.md` (the row, source of truth) and the ↗ pointer into `_route.md` (manifestation). One read-only touch: the route-map (to resolve a ref). One project-wide read: the glob (guard + `list`).

**Foundational Principles (axioms):**
- FP1 — Records-and-points, never chooses-or-launches ("I am the meta loop still").
- FP2 — Mechanize the closing step or it doesn't happen (measured: zero-for-109).
- FP3 — Truth lives where the fact is local; the project view is derived, never a maintained second truth.

**Meaning-Nodes (central concepts):**
- MN1 — rlu = the **route-engagement recorder + pointer**.
- MN2 — The **single-decider bright line** (the spine of "shouldn't be").
- MN3 — The **generative scenario-axes** (the spine of "in what scenarios").
- MN4 — The **route-engagement lifecycle** (the spine of "should do").

## Phase 2 — Perspective Checking

- **Technical / Logical:** A state-machine + append-only log is the right shape — current state = last row mentioning the ref; crash-safe; reconstructable. The glob is O(folders) and cheap-enough; concurrency (parallel writers to one file) is the only technically-thorny case → frontier.
- **Human / User:** The user's real pain is the *closing step* (the run happens, the record doesn't). The design must make `done` trivial and `start` near-free, and must *catch* the human when they forget (the sweep). Friction at the recording moment defeats the whole tool.
- **Strategic / Long-term:** rlu is the first deployed write-tool of the larger SUSTRALL machine; its discipline (record-and-point, append-only, derived-view) sets the pattern the future Dispatcher/Selector inherit. Getting the bright line right now prevents a tangled multi-decider later.
- **Risk / Failure:** The dangerous failure is **silent scope-creep into deciding** (rlu starts ranking/choosing/judging) — it corrupts decision-authority invisibly. The second risk is **the irreversible pre-registration window** (a first engagement-record written before the pre-registration file, where declared). Both are guarded by explicit behaviors, not vibes.
- **Resource / Feasibility:** Day-1 cost must stay tiny: two commands + a view. The pillars are the "why"; the interface is `start`/`done`/`park`/`list`. Over-spec'ing the frontier (concurrency, project-level routes) now would bloat v1 — defer with named gates.
- **Definitional / Internal Consistency:** Does "records-and-points" contradict "auto-collects metadata"? No — metadata is the *path + timestamps* of what already happened (pointing), not a *judgment* of it. Does "append-only" contradict "current state"? No — current state is a *read* (last row), not a rewrite. Consistent.
- **Phase / Calibration-State:** The window guard is phase-dependent — it hard-STOPs only where a pre-registration program is declared (native project), warns elsewhere (crowboy). Early-stage default: warn-everywhere + stop-where-declared. Correct for the project's current state (pre-registration not yet active globally). No calibration data is required for rlu's core behavior; only the guard's strictness is phase-keyed.

### SV3 — Multi-Perspective Understanding

The perspectives converge on a sharpened model with one genuine tension surfaced (concurrency/parallel-writers → frontier) and one risk elevated to a first-class behavior (scope-creep-into-deciding must be *actively* fenced, not just declared). The Human and Resource views jointly demand: **the contract is three derivable pillars, but the day-1 surface is small** (start/done/park/list). The Strategic view raises the stakes: rlu's bright line is the template for the whole machine. No perspective destabilized the three-pillar model — they refined it. (Checked the uncomfortable perspective — Risk — and it *added* the active-fence behavior rather than collapsing the model, so this isn't perspective-blindness.)

## Phase 3 — Ambiguity Collapse

#### Ambiguity 1 — Is the "shouldn't be" a flat taboo-list or derivable from one principle?
**Strongest counter-interpretation:** It's just a list of specific don'ts (don't edit the map, don't write to `_route.md`, etc.) — each a separate rule with its own reason; forcing them under one principle is false elegance (anchor-dominance risk).
**Why the counter fails (structural):** Test each: don't-choose, don't-launch, don't-judge-content, don't-maintain-forward-queue — every one is an instance of "rlu must not exercise or pre-empt decision authority." But don't-mutate-the-map and don't-write-status-into-`_route.md` are NOT decision-authority items — they're *data-integrity* items (P2). So the NOT-list has **two roots, not one**: P1 (single-decider) covers the behavioral don'ts; P2 (integrity) covers the artifact-touch don'ts. That two-root finding is exactly what rebuts anchor-dominance — one principle does NOT do all the work.
**Confidence:** HIGH.
**Resolution:** The NOT-list is derivable, from **two** pillars: P1 (single-decider) for behavior-don'ts, P2 (integrity) for touch-don'ts. State the principle, then list the corollaries.
**What is now fixed?** "Shouldn't-be" is organized under P1 + P2, each corollary tagged to its root.
**What is no longer allowed?** Presenting the NOT-list as arbitrary; adding a don't without rooting it in a pillar.
**What now depends on this?** The spec's "shouldn't be" section structure; the active scope-fence behavior.
**What changed in the model?** Confirmed multi-anchored (≥2 pillars behind the NOT-list alone).

#### Ambiguity 2 — Is the scenario set closed (the named ones) or generated?
**Strongest counter-interpretation:** Just enumerate the scenarios we listed (informal, forgotten-start, crash, cross-inquiry, first-run, parked) — a table is what the user asked for; "axes" is over-abstraction.
**Why the counter fails (structural):** A flat table answers "these scenarios," but the user's WHY-axis was **coverage-driven** ("in what scenarios" = worry about *unhandled* cases). A closed table cannot demonstrate completeness; an axis-space can (every named scenario is a coordinate; unnamed scenarios are un-instantiated coordinates). The specific-vs-pattern cue: the six named cases are *examples of* a wider situation-space, not the whole of it.
**Confidence:** HIGH.
**Resolution:** Specify the **generative scenario-axes** (A1–A7), then instantiate the important coordinates as the scenario→behavior table. The table is the *examples*; the axes are *the coverage guarantee*.
**What is now fixed?** Scenarios are presented as axis-coordinates + an instantiated table.
**What is no longer allowed?** Claiming coverage from a flat list alone.
**What now depends on this?** The "in what scenarios" section; the completeness argument; Critique's coverage check.
**What changed in the model?** "Scenarios" became a generated space (MN3), dissolving the coverage worry.

#### Ambiguity 3 — Build-ready contract vs stress-test vs boundary-draw?
**Strongest counter-interpretation:** Pick one — a build-ready contract is a different artifact from a gap-finding stress-test.
**Why the counter fails (structural):** A scenario-driven contract *is* the gap-finder: walking rlu through every axis-coordinate is simultaneously how you finalize behavior AND expose where it's silent. Boundary-draw is just the P1/P2 face of the same contract. They are three views of one document, not three documents. (This is the MQA-surfaced irreducible overlap, now resolved as "one artifact, three views.")
**Confidence:** HIGH.
**Resolution:** Produce one contract that is build-ready, and whose scenario-walk *is* the stress-test, and whose pillar-rooting *is* the boundary.
**What is now fixed?** One deliverable, three views.
**What is no longer allowed?** Treating depth-target as an either/or.
**What now depends on this?** Decomposition's piece structure (one spec, faceted).
**What changed in the model?** The depth-target ambiguity dissolves.

#### Ambiguity 4 — Cross-inquiry / project-level / concurrency: in scope now or deferred?
**Strongest counter-interpretation:** All three are edge cases; defer them all to keep v1 small.
**Why the counter fails (structural):** Distinguish **specifying the rule** from **building the machinery**. Cross-inquiry placement is a *rule* (row lives where-it-ran + source-map back-ref) that must be stated now — informal cross-inquiry runs happen on day 1 (the user's own case). But project-level-route homing (A7) and parallel-writer concurrency (A6 extreme) need *machinery* tied to the deferred Navigator/Dispatcher — defer those. So it splits: state the cross-inquiry placement rule NOW; defer project-level-homing + parallel-concurrency with named gates.
**Confidence:** MED-HIGH (the split is clear; the exact concurrency gate is fuzzy).
**Resolution:** In-scope-now: cross-inquiry placement rule, single + sequential-multi cardinality. Deferred (named gates): project-level-route homing (gate: Navigator real), parallel-writer concurrency (gate: Dispatcher real).
**What is now fixed?** v1 scope boundary on the scenario axes.
**What is no longer allowed?** Either deferring the cross-inquiry rule, or building concurrency machinery into v1.
**What now depends on this?** The scenario table's "ships-now vs deferred" column.
**What changed in the model?** A6/A7 partially deferred; A3 (cross-inquiry) confirmed in-scope.

#### Ambiguity 5 — Does rlu read the produced finding's CONTENT?
**Strongest counter-interpretation:** To write a good one-line outcome, rlu must read and summarize the finding — so it does consume content.
**Why the counter fails (structural):** Writing a one-line outcome from what the *session* already produced is *transcription/pointing*, not *judgment*. The bright line (P1) is about **deciding** — rlu must not read a finding *to evaluate or rank or choose next*. It may capture the path + a human/session-supplied one-liner; it must not form an opinion that feeds a selection. The distinction is "point at the outcome" vs "judge the outcome." rlu does the former.
**Confidence:** HIGH.
**Resolution:** rlu captures path + timestamps + a session-supplied one-line outcome; it never reads-to-judge or reads-to-rank.
**What is now fixed?** The metadata/judgment boundary.
**What is no longer allowed?** rlu forming an evaluative opinion of an artifact.
**What now depends on this?** The `done` behavior; the N7 NOT-list item.
**What changed in the model?** P1's bright line sharpened to "point, don't judge."

#### Ambiguity 6 — Is rlu code, or a session-invoked skill?
**Strongest counter-interpretation:** It should be deterministic code (a script) — recording is mechanical, and code runs without burning a session/context.
**Why the counter fails (structural):** rlu must resolve a route-ref against the route-map (read + disambiguate, sometimes *ask*), write prose rows, stamp a manifestation pointer, and judge "is this the project's first engagement-record" — these need light reasoning + interaction, i.e., a skill invoked in the session where the work happened. BUT the *formal-loop* case can be mechanized: the `/aMVLwr` runner appends the completion mark itself at CONCLUDE (Enhancement 1), no separate rlu invocation. So: **rlu is a session-invoked skill; the formal-loop path can delegate the mark to the runner.** (This touches the structural layer — flagged for a possible follow-up structural pass, per the Layer Commitment.)
**Confidence:** MED (core stance HIGH; the code-vs-skill *interface* detail is structural and deferred).
**Resolution:** rlu = a session-invoked skill (records-and-points with light reasoning + ask-on-ambiguity); formal-loop completion may be auto-marked by the runner.
**What is now fixed?** rlu is a skill, not pure code; the runner-integration path exists.
**What is no longer allowed?** Assuming rlu is a silent background script.
**What now depends on this?** The interface sketch; the `/aMVLwr` integration item.
**What changed in the model?** Confirmed I4 (skill, runs where work runs).
