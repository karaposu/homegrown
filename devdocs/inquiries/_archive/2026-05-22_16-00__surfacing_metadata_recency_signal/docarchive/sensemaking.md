# Sensemaking — Metadata-Recency Addition to /surfacing

## User Input

(from `_branch.md`) What addition to surfacing.md — at what exact location — would let surfacing use file mtime as a signal during traversal, while protecting against (a) treating old-as-idle AND (b) silently down-weighting older items, such that existing behavior is enriched not regressed?

## Initial Sense Version (SV1)

The user wants surfacing to USE file last-modified time as a signal, with two explicit guard-rails: don't conflate old-with-idle, don't silently demote old. The addition should be a concrete spec edit, not a hand-wave. At first reading, this looks like "add an mtime field somewhere" — but where, and with what semantics, and how to prevent regression, is the actual work.

---

## Phase 1 — Cognitive Anchor Extraction

### Constraints

- **C1 — No filter.** mtime must not gate items out of the workspace ("skip if older than N days" is forbidden).
- **C2 — No monotonic demotion.** mtime must not reduce the relevance tag ("if older than N days, demote one level" is forbidden).
- **C3 — No recency-only mode.** The addition must not create a mode where only-recent items get surfaced and the rest of the territory is silently dropped.
- **C4 — Existing behavior reachable.** Surfacing's current recency-blind operation must remain available — the addition is enrichment, not replacement.
- **C5 — Asymmetric-failure preservation.** The existing principle ("missing relevant is worse than surfacing irrelevant," surfacing.md §4.4) must extend to the recency axis: an old-but-relevant item missed because of mtime treatment is a Type-2 information-loss failure.
- **C6 — Self-contained spec.** The addition lives within `cognitive_harness/surfacing/references/surfacing.md`; no outbound pointers to design-history folders (per the project's "disciplines self-contained" rule).
- **C7 — Discipline taxonomy slot preserved.** Surfacing stays Core; the load-bearing primitive profile (8 primitives) stays unchanged; no new primitive is admitted.

### Key Insights

- **KI1 — mtime is an ORTHOGONAL THIRD AXIS.** Surfacing already operates on two orthogonal axes: (i) content-vs-purpose (the relevance tag) and (ii) content-vs-correctness (excluded from surfacing — NOT-list §1.3). mtime is a THIRD orthogonal axis: time-of-last-edit. None of the three axes adjudicates the others. The addition's correctness depends on naming this orthogonality and refusing to collapse it.
- **KI2 — The per-item output schema is ADDITIVE.** The Traversal Trace currently carries `{ordinal, region, identifier, tag, confidence, step note}`. Adding one more per-entry field (a recency annotation) is the natural, minimum-disruption shape. No primitive change required; no process restructure.
- **KI3 — The asymmetric-failure principle ALREADY rejects mtime-as-filter.** Filtering by mtime creates false-negatives (old-but-relevant items dropped). The existing principle (§4.4) explicitly classifies false-negatives as the worse failure. The two new failure modes are direct INSTANCES of the existing principle applied to the recency axis — not new principles.
- **KI4 — The Placement convention TELLS US where the addition lives.** Per `docs/discipline_rule_placement.md`: rules that apply to ALL instances of an operation go at the operation's Component sub-section. mtime-capture applies to ALL instances of Item-enumeration. Therefore the per-item capture rule lives at §2.1 Item-enumeration. The two new failure modes live at §4.2 LAYER 1. The schema field lives at §5.4. These three placements are forced by the existing convention, not invented.
- **KI5 — mtime captures AT MOMENT-OF-ENUMERATION, not at AT-MOMENT-OF-RELEVANCE-TAGGING.** The relevance-attribution mechanism (§2.3) is content-driven; injecting mtime into its five steps would conflate. mtime is a property captured when the item is first touched (Item-enumeration §2.1), and emitted to the Trace alongside the tag at Output-shaping. The relevance tag remains generated by content+purpose alone.
- **KI6 — The Step Refinement primitive is the right vehicle.** Per `docs/step_refinement.md`, the 4-element shape (Name + Trigger + Action + Anchor-link) with italic visual marker is exactly the right form for the new rules. Failure-anchored subtype (citing the two new failure modes by name) keeps the spec internally consistent.

### Structural Points

- **SP1 — The dual output is preserved.** Workspace stays session-local in-context content; artifact stays thin (no item content). mtime annotation goes in the thin artifact (per-entry field on Traversal Trace, derived field on State Summary). Workspace consumption stays text-content-driven; mtime is reportable to downstream but does not change what's IN the workspace.
- **SP2 — Three structural surfaces are touched.** Component §2.1 (Item-enumeration: capture mtime alongside identifier); Failure-mode §4.2 (two new entries); Output §5.4 (Traversal Trace schema gets one new per-entry field) + §5.5 (State Summary gets one derived recency-distribution field).
- **SP3 — The vocabulary section §1.4 stays accurate by adding one entry.** Currently 7 vocabulary entries; adding one ("recency annotation" or equivalent) keeps the user-facing terms list aligned with the schema.
- **SP4 — Telemetry §5.6 is the natural reporting surface.** Aggregate counts of items at each recency band, alongside the existing tag-level counts.

### Foundational Principles

- **FP1 — Metadata-as-signal-not-verdict.** Metadata enriches the per-item annotation; it never replaces or filters the relevance tag. This is the load-bearing principle of the entire addition. State it explicitly in the spec so future contributors don't drift.
- **FP2 — Mtime missingness is first-class.** A file with no obtainable mtime (e.g., synthesized item in possibility mode, or external reference without filesystem backing) must carry a "no mtime available" annotation, not be excluded or treated as missing data. This is the recency-axis analog of the asymmetric-failure principle.
- **FP3 — Recency is a DESCRIPTIVE annotation, not a JUDGMENT.** The annotation reports observed mtime (or a recency band derived from it) without verdicting that an item IS-or-IS-NOT idle. Idleness vs. activity is an interpretation downstream consumers can make; surfacing emits the signal, not the verdict.

### Meaning-Nodes

- **MN1 — `recency annotation` (proposed term).** The new per-item field. Carries mtime (or a derived band: recent/aged/ancient/no-mtime).
- **MN2 — `Recency-Equates-Idleness` (proposed failure-mode name).** The LAYER 1 mode where the discipline (or its consumer) treats mtime-old as relevance-low without independent evidence.
- **MN3 — `Recency-Bias-Filter` (proposed failure-mode name).** The LAYER 1 mode where mtime is used to filter or down-weight items, creating false-negatives.
- **MN4 — `Active-Task indication`.** The legitimate use-case for the annotation: recent edits SUGGEST where active work is happening; the annotation supports this without enforcing it.

### Meta-Inspection (after SV2)

- **H4 (concept names).** Are the names — `recency annotation`, `Recency-Equates-Idleness`, `Recency-Bias-Filter` — load-bearing? Tested below in Phase 3 Load-bearing concept test.
- **H5 (motivating examples).** The user named two specific manifestations: "idle artifacts in the codebase" and "recently edited files = active task." Specific-vs-pattern: the broader pattern is metadata-as-orthogonal-third-axis. The specific manifestations are two USE-CASES of that broader pattern, not the whole pattern. Tested below in Phase 3 Specific-vs-pattern recognition cue.

### Sense Version 2 (SV2 — Anchor-Informed Understanding)

The question is structurally well-shaped: mtime is an orthogonal third axis (alongside content-relevance-to-purpose and the deliberately-excluded content-correctness). The existing schema is additive; the existing convention determines placement; the existing asymmetric-failure principle already protects against the regression risks the user names. The work is not "design a new mechanism" — it's "add three specific named items at three specific locations in the spec, and state the orthogonality principle explicitly so it doesn't drift." The user's question is a refinement, not a redefinition.

## Phase 2 — Perspective Checking

mtime is filesystem-deterministic. The capture is `stat()`-equivalent — zero ambiguity for items that have a filesystem backing. For items that don't (possibility-mode candidates, externally-referenced sources without local file), the value is "no mtime available." A two-state existence check before each annotation; no failure modes from the capture itself.

### Human / User

The user's framing distinguishes two desirable behaviors (mtime as relevance signal, mtime for active-task spotting) from two regression behaviors (old=idle, silent down-weighting). Their framing is precise — they have already done part of the design work. The spec edit should make this precision permanent.

### Strategic / Long-term

If recency-aware surfacing is generalizable, the same orthogonal-third-axis pattern applies to OTHER metadata signals (file size, author, git-blame age, edit-count-per-week, etc.). Long-term: this addition is a TEMPLATE for metadata-as-signal additions, even though we're shipping only the mtime instance.

## Phase 3 — Ambiguity Collapse

### Ambiguity #1 — name of the new per-item field

The proposed term is "recency annotation." Alternatives: "mtime annotation," "metadata annotation," "edit-recency tag," "freshness field."

**Strongest counter-interpretation:** "mtime annotation" is more precise — it tells contributors EXACTLY what's captured (the filesystem mtime, not some derived freshness judgment), avoiding the trap where "recency" gets reinterpreted as "freshness" downstream and pulled toward verdict-like uses.

**Why the counter-interpretation fails (structural grounds):** mtime is the IMPLEMENTATION; the spec should name the SIGNAL the field carries, not the implementation. For possibility-mode items that have no mtime, the field still exists (with a "no mtime available" annotation); calling the field "mtime annotation" misleads when no mtime exists. The signal is recency information (which may or may not derive from mtime); the field name should reflect the signal, not the source.

**Confidence:** MEDIUM (both readings have merit; choosing the signal-name keeps the spec source-agnostic and forward-compatible if other sources of recency signal appear).

**Resolution:** Use `recency annotation` as the field name. State explicitly in the spec that "the primary source for the recency annotation is filesystem mtime when available, with 'no mtime available' as a first-class value for items without filesystem backing."

**What is now fixed:** The field name. The signal-source generality.

**What is no longer allowed:** Naming the field after its implementation (e.g., `mtime_field`).

**What now depends on this choice:** The vocabulary entry (§1.4), the schema field (§5.4), the failure-mode names (which use "Recency" as the prefix and stay consistent with the annotation name).

**What changed in the conceptual model:** The annotation is a signal, not a source. Implementation details can vary; the spec's commitment is to the signal.

### Ambiguity #2 — failure-mode names

Proposed: `Recency-Equates-Idleness` and `Recency-Bias-Filter`. Alternatives considered: `Old-Equals-Idle`, `Recency-Conflation`; `Mtime-As-Filter`, `Recency-Down-Weighting`.

**Strongest counter-interpretation:** Shorter names (`Recency-Conflation` and `Mtime-As-Filter`) are easier to remember and reference; the longer forms are over-engineered for the spec's tight prose style.

**Why the counter-interpretation fails (structural grounds):** Short names hide the mechanism. `Recency-Conflation` doesn't tell the reader WITH WHAT recency is conflated. `Mtime-As-Filter` is implementation-specific (excluded above per Ambiguity #1's resolution). The longer forms each encode the mechanism (X-Equates-Y, X-Bias-Z) so a reader skimming the failure-mode list can identify the structural risk without reading the body.

**Confidence:** HIGH (the mechanism-encoding shape is the project's existing failure-mode-naming convention — e.g., "Self-coupling-to-downstream," "Workspace-artifact desync" — and matches it).

**Resolution:** `Recency-Equates-Idleness` and `Recency-Bias-Filter` as the failure-mode names.

**What is now fixed:** Both names.

**What is no longer allowed:** Renaming to implementation-specific or mechanism-hidden forms.

**What now depends on this choice:** Anchor-link sentences in the Step Refinements (failure-anchored subtype cites these names by full phrase).

**What changed in the conceptual model:** The two failure modes are now first-class named entries; the visual marker convention (italic prefix) applies; future Step Refinements can anchor to them.

### Ambiguity #3 — should mtime be a NEW PRIMITIVE in §2.4

**Strongest counter-interpretation:** mtime is a per-item attribute that flows through the discipline; a new primitive ("Metadata-channel" or "Time-signal") would make it first-class in the typed primitive set, signaling its load-bearing role.

**Why the counter-interpretation fails (structural grounds):** Per `docs/thinking_space_dynamics.md`, primitives are admitted via the four-criterion test (independence, necessity, composability, irreducibility) with a corpus-located audit. mtime fails Necessity at minimum: it's a deterministic filesystem fact retrievable via Attention-pointer (which already selects items) and Working Memory (which already holds item state). No new cognitive primitive is required. Adding one would inflate the typed set; the taxonomy explicitly cautions against this (the 4-primitive model was killed for collapsing distinctions; the 11-primitive model is "good enough to build on, not philosophically final" — additions need real necessity).

**Confidence:** HIGH.

**Resolution:** No new primitive. The addition composes from existing primitives (Attention-pointer captures the metadata when reading the item; Working Memory holds it; Output-shaping emits it to the Trace).

**What is now fixed:** The primitive set stays at 11; surfacing's load-bearing 8 stays unchanged.

**What is no longer allowed:** Introducing a new primitive for mtime.

**What now depends on this choice:** The placement at Component §2.1 (Item-enumeration captures the data; no separate component for "metadata capture").

**What changed in the conceptual model:** The addition is at the OPERATIONAL surface (Component / Process / Failure / Schema), not the PRIMITIVE surface. The taxonomy slot for surfacing is preserved.

### Ambiguity #4 — should the annotation be MANDATORY per item, or OPT-IN

**Strongest counter-interpretation:** Mandatory annotation per item is unnecessary overhead — for possibility-mode candidates (which never have mtime), the field would be "no mtime available" 100% of the time, adding noise without signal.

**Why the counter-interpretation fails (structural grounds):** Optional-per-item creates schema inconsistency: some entries have the field, some don't. Downstream consumers can't depend on the field's presence. The asymmetric-failure principle prefers schema completeness with explicit "no value" markers over schema heterogeneity. A "no mtime available" value is structurally meaningful — it carries information ("this item has no filesystem backing").

**Confidence:** HIGH (mirrors the spec's existing handling of unknown values — `populated: <bool>`, frontier flags, confirmed-absent regions — all explicit-marker rather than omitted-when-empty).

**Resolution:** Mandatory per-item annotation, with `no-mtime-available` as a first-class value.

**What is now fixed:** Schema field is mandatory; values include `no-mtime-available` alongside actual mtimes.

**What is no longer allowed:** Omitting the field for items without filesystem backing.

**What now depends on this choice:** The Output-shaping rule (always emit the annotation); the State Summary derived field (must report counts including "no mtime available" alongside the dated counts).

**What changed in the conceptual model:** Missingness is information; surfacing reports it.

### Refinement Note Cross-Reference: Load-bearing concept test

The three load-bearing concept names — `recency annotation` (Ambiguity #1), `Recency-Equates-Idleness` and `Recency-Bias-Filter` (Ambiguity #2) — were each tested against:

- **proxy-vs-structural:** Each name describes a real structural distinction (signal-not-source; mechanism encoded). Not proxies.
- **discoverability:** Each name appears in the Step Refinement's anchor-link sentence; readers find the failure mode at the failure-mode-list and follow back to the rule. Discoverable.
- **user-language alignment:** The user used "metadata," "last datetime of edit," "idle artifacts," "active task." `recency annotation` aligns with "metadata"; `Recency-Equates-Idleness` aligns with "idle." Aligned.

### Refinement Note Cross-Reference: Specific-vs-pattern recognition cue

The user named two specific manifestations: "idle artifacts" and "active task." Specific-vs-pattern:

**The broader pattern is metadata-as-orthogonal-third-axis.** "Idle artifacts" is one consequence (false-positive interpretation that the user wants to enable detecting). "Active task" is another consequence (the legitimate use case). Neither IS the whole pattern; both are USES of it.

The design must address the broader pattern (orthogonality + metadata-as-signal-not-verdict) and produce the specific manifestations as derivable consequences. The user's framing already implies this — they ask for the "kind of thing" not for the specific cases.
