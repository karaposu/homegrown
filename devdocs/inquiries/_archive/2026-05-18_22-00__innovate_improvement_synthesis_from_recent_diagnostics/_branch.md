## Layer Commitment

**Primary layer: MEANING.** The load-bearing question is *what capability or concept is `/innovate` missing that would make it more useful for traversing thinking space*. The improvements being generated are MEANING-level (what does Innovation need to be able to do that it currently can't) with structural (where the addition lives in the spec) and process (what steps it adds) implications downstream from each accepted improvement.

Sequential plan:
1. **Meaning layer** (this inquiry): identify ≥3 capability gaps in /innovate's meaning surface; characterize each at meaning-level with cumulative-evidence grounding.
2. **Structural layer** (follow-on per accepted improvement): each accepted improvement gets a downstream spec-edit inquiry deciding how it lives in `cognitive_harness/innovate/references/innovate.md` — what section, what wording, what cross-references.
3. **Process layer** (follow-on per accepted improvement): each accepted improvement's procedural integration (what steps it adds; what triggers it; what compliance criterion makes it artifact-observable).

Other layers explicitly out of scope for THIS run:

- **Structural** — concrete spec-edit wording is downstream; this inquiry produces capability-level proposals, not edit-spec text.
- **Process** — procedural integration is downstream; this inquiry doesn't specify steps or compliance criteria.

The meaning layer is primary because the user's framing ("understand how we can improve... what is missing... what new aspects we understand... seeds for future improvements") is epistemic/conceptual — it asks WHAT capabilities are needed, not HOW to write them into the spec.
