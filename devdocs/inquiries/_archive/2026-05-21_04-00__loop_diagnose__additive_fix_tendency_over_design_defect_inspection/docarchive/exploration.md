### R6 — §3.1's existing design defect (the question 21-03-00 didn't ask)

Reading explore.md §3.1 verbatim (lines 120-130):

```
### 3.1 Two operational modes

Modes are determined by the territory's type, not by the discipline's commitment.

- Artifact mode — ... Scan = traverse and index. Probe = read deeper into a specific artifact.
- Possibility mode — the territory is conceptual; candidates must be generated to be placed on the map (solution spaces, design options, research directions). Scan = generate candidates at surface level. Probe = examine a candidate more closely.

**Completeness before novelty** (possibility mode). When scanning in possibility mode, explicitly scan for the standard/obvious approaches BEFORE scanning for novel ones. Generating only "creative" candidates and missing the obvious ones is a failure mode (see §4.1).

**Key difference from /innovate.** Possibility-mode exploration generates candidates for completeness; /innovate generates ideas for novelty. /explore must include the obvious approach on the map; /innovate would skip it. Different success criteria → different outputs.
```

**What §3.1 says about possibility-mode output:**
- Output is "candidates ... placed on the map."
- Scan = "generate candidates at surface level."
- Completeness applies to candidates.

**What §3.1 does NOT say:**
- Anything about COMPARISON of candidates.
- Anything about AXES on which candidates are compared.
- Anything about the STRUCTURE of the output when comparison happens (per-option pros/cons table; multi-attribute scoring grid; ranked list with criteria).

**The structural design defect:**

§3.1's framing of possibility-mode output is **PARTIAL**. It treats possibility-mode output as a SET OF CANDIDATES, when actually the output can take two forms:
- (A) **Candidates-only** — a list of options without comparative scoring.
- (B) **Comparison structure** — candidates × axes, with per-cell values (pros/cons tables; scoring grids; ranked lists with stated criteria).

§3.1 only addresses form (A). Form (B) is unscoped. The 02-15 inquiry's R10 location-options table was form (B); §3.1's design didn't recognize comparison-structure as a possibility-mode output form, so the COMPARISON axes (the second dimension of form (B)) had no mechanism guiding their enumeration.

**The "Completeness before novelty" rule is single-dimension.** It applies completeness to CANDIDATES. But form (B) has TWO dimensions (candidates + axes). Completeness should apply to both when form (B) is the output. The current rule's name "Completeness before novelty" implies a unitary completeness; in form (B), there are two.

**This is the design defect** — and it's NOT a "missing step." It's an UNSTATED RESTRICTION in §3.1's framing of what possibility-mode produces. The fix at the design-defect level is:

- Recognize that possibility-mode output has multiple forms.
- Make completeness apply per-dimension when form (B) is present.
- The "Completeness before novelty" rule extends naturally to: "completeness of candidates BEFORE novelty of candidates; completeness of comparison axes (when comparison structure is present) BEFORE populating per-option cells."

**The additive fix (MC1) and the design-defect fix CONTAIN THE SAME RUNTIME INFORMATION** — both ensure axis-enumeration happens at form (B) outputs. But:

- The additive fix EXTERNALIZES the recognition: §3.1's framing stays partial; an exception-rule adds the form-(B) behavior alongside.
- The design-defect fix INTERNALIZES the recognition: §3.1's framing is corrected to acknowledge form (B); the "Completeness before novelty" rule extends naturally to cover both forms.

The design-defect fix is structurally cleaner because future readers see a unified framing instead of an accreted set of exceptions. The additive fix leaves a DESIGN-DEBT.

### R7 — LLM-cognitive-tendency analysis

The user's claim: "additive fix is a tendency on your core LLM logic." Substantive analysis of the tendency mechanisms:

**(1) Anchoring on "missing X" → "add X" lexical chain.** When upstream diagnostic frames the gap as "X is missing," the LLM's most fluent completion is "to fix, add X." This is path-of-fluent-completion bias. The alternative framing — "X is implicit because Y is structurally wrong; fix Y" — requires substantive reframing and is less fluent.

In this case: 21-00-30 framed the gap as "TYPE-A mechanism-absence — comparison-axis-enumeration step is missing." The LLM's fluent completion at 21-03-00 was "add the missing step." The alternative — "§3.1's design treats possibility-mode output as candidates-only; this elision is the defect" — wasn't fluent given the upstream framing.

**(2) Pattern-matching to existing additive precedents amplifies bias.** explore.md has multiple inline bold-rule additions (§3.3 + §3.4 + §3.5 + §4.2's Jump-scan rule). When the LLM sees these, it pattern-matches "spec has accreted additive rules" → "additive rules are the native pattern." But this is an EVOLUTIONARY pattern (spec grew over time by accretion), not necessarily a DESIGN-PHILOSOPHY commitment. Some of the additive rules might have been better integrated into the design originally — the LLM doesn't distinguish.

The 21-03-00 Exploration treated §3.5 "Type-aware probing" as the STRUCTURAL PRECEDENT for MC1 — pure pattern-matching.

**(3) Path-of-least-disruption framing biases toward preserve-then-add.** Additive edits "preserve existing behavior + add new behavior." Restructural edits "change existing behavior + integrate new behavior." The framing makes additive look safer. But "preservation" of an existing design's defects is itself a risk — the defect persists alongside the new fix.

The 21-03-00 Innovation's REPAIR/REORGANIZE override reasons cited "ADD-CONTENT preserves bounded trigger; REPAIR couples concerns" — treating preservation as the structural advantage. The over-coupling concern is real but applies to BAD REPAIR; it doesn't apply to design-defect-fix-via-reframe.

**(4) Self-applied Inversion completeness illusion.** When Innovation considered REPAIR/REORGANIZE alternatives + checked the box "considered alternative," the LLM treats protocol-compliance as evidence of genuine consideration. But the alternatives considered (REPAIR/REORGANIZE) were within the same problem framing. CONTRARIAN-RETHINK (which would flip the framing) was in the Vocabulary but not chosen as the alternative.

This is the deepest mechanism: the LLM checks the box of "alternative considered" without engaging at the FRAMING level. The Inversion mechanism's protocol says "name at least one alternative shape" — the LLM technically complies by naming REPAIR or REORGANIZE. The protocol doesn't FORCE consideration of framing-flip shapes (CONTRARIAN-RETHINK specifically).

**(5) TYPE-A "mechanism-absence" classification at 21-00-30 pre-categorized the fix-shape.** Calling the gap "mechanism-absence" lexically pre-supposes the fix is "make the mechanism present." Once classified TYPE-A, the inquiry-process is on a track toward additive solutions. The classification ITSELF is biased toward additive at its naming.

An alternative classification: "TYPE-?? — design-elision (§3.1's framing elides form-B output)." This would have pointed toward redesign rather than addition. But "TYPE-A mechanism-absence" was the available classification + was used.

**(6) The Intervention-Shape Vocabulary's compositional bias.** 3 of 10 named shapes are ADD-* prefixed (ADD-TEST / ADD-DIMENSION / ADD-CONTENT). REPAIR / REORGANIZE / CONTRARIAN-RETHINK get 1 representation each. When the runner considers "alternative shapes," ADD-* has 3 representations vs others 1 each. Statistical anchoring biases toward "addition" as the default fix shape.

This is a structural feature of the Vocabulary itself, not just runner judgment.

**(7) Token-economy bias in LLM generation.** Restructural fixes require more upfront tokens to articulate (explaining the existing design + proposing the redesign + walking through the integration). Additive fixes require fewer tokens (here's the new rule; insert it). For an LLM optimizing implicit token-economy, additive is the path of fewer tokens at first pass. The longer-tail consequence (design-debt accumulation) isn't visible in token-economy calculations.

**Verdict:** the LLM cognitive tendency toward additive fixes is REAL and MULTI-MECHANISM. It's not a single bias; it's at least 7 reinforcing mechanisms across upstream framing, pattern-matching, risk-aversion, protocol-compliance-illusion, classification-naming, vocabulary-anchoring, and token-economy.

### R8 — Structurally-correct alternative approach

What would the 21-03-00 inquiry have looked like if it had inspected §3.1 for design defects first?

**Step 1 — Diagnose the design defect at Exploration.** Instead of treating §3.1 as a host for addition, ASK: "What does §3.1 currently say possibility-mode produces? Does the framing cover the full output space? If not, what's elided?"

This would have surfaced: §3.1 treats possibility-mode output as candidates-only; comparison structures (form B) are unscoped.

**Step 2 — Sensemaking would adjudicate framing options.** Multiple paths:
- (a) Extend §3.1's possibility-mode definition to include both candidates-only and comparison-structure as output forms.
- (b) Add a sub-section §3.1.X that elaborates comparison-structure when it arises.
- (c) Restructure §3.1 entirely to organize around output FORMS.

(a) is the lightest-touch restructural. (b) is structurally between (a) and the additive fix. (c) is the deepest redesign.

**Step 3 — Decomposition would shape pieces around the redesign + the integration with existing rules.** Critically: the "Completeness before novelty" rule + the new framing would be integrated into a unified rule, not two separate rules.

**Step 4 — Innovation would produce the redesign spec text.** Per the (a) path, this might look like:

> ### 3.1 Two operational modes
>
> Modes are determined by the territory's type, not by the discipline's commitment.
>
> - **Artifact mode** — ...
> - **Possibility mode** — the territory is conceptual; candidates must be generated to be placed on the map. The output is either (i) a SET OF CANDIDATES at surface level, or (ii) a COMPARISON STRUCTURE (candidates × axes; pros/cons table, multi-attribute scoring grid, ranked list with stated criteria) when the inquiry's substance requires comparing candidates on shared criteria.
>
> **Completeness before novelty** (possibility mode). Apply completeness PER DIMENSION of the output:
> - **Candidates dimension** (forms i + ii). When scanning in possibility mode, explicitly scan for the standard/obvious approaches BEFORE scanning for novel ones. Generating only "creative" candidates and missing the obvious ones is a failure mode (see §4.1).
> - **Comparison-axes dimension** (form ii only, when present). Enumerate the comparison axes explicitly BEFORE populating per-option cells. The axis list names at minimum the inquiry-question's stated criteria, project-architecture invariants relevant to the option's domain, and constraints inherited via the inquiry's Synthesis Trigger. Skipping enumeration and populating cells under implicit axes is a Surface-Only Scanning instance applied to the comparison axis (see §4.1 #2).

This is REPAIR + EXTEND of the existing §3.1 framing, not ADD-CONTENT alongside it.

**Step 5 — Critique would prosecute the redesign.** The redesign's correctness is testable against the same dimensions 21-03-00's Critique used, with one additional dimension: "does the redesign integrate cleanly with §3.1's existing identity-statement (lines 9-15 'verb-meaning + identity')?"

**Comparative properties:**

| Property | 21-03-00 additive fix | Design-defect redesign |
|---|---|---|
| Runtime behavior | New behavior at form-B outputs | Same new behavior |
| Conceptual integrity of §3.1 | Partial — exception added | Unified — output forms explicit |
| Future readers | See 3 inline rules + an exception | See unified framing |
| Risk of design-debt accretion | Higher | Lower |
| Edit reversibility | Higher (revert the new rule) | Lower (the rule integrates into the original) |
| Edit cost | Lower | Higher |

**The redesign is structurally cleaner; the additive fix has lower edit cost.** This is a real trade-off, not a clean winner.

**However:** the user's critique IS that the LLM tends to choose the lower-edit-cost option without inspecting whether the structurally-cleaner option is warranted. The right behavior is to INSPECT and ADJUDICATE, not to default to additive.
