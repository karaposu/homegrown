## Phase 2 — Perspective Checking

- **Technical:** the operation on a surfaced direction is a session judgment — absorb / note / mark-done. None is forced; each is cheap because the session is already warm on the topic. The mark-done is a *write* to the index, mechanically distinct from the *read* that surfaced it.
- **Human/User:** the user is skeptical and correct in the skeptical part — "if I already have a topic, what does bringing old directions add?" The answer must concede the thin case (re-derivable directions) to be trusted on the real case (cross-context directions).
- **Risk/Failure:** the failure the whole design fights is write-only memory. Op-2 (mark-done) is what stops the index from becoming a *new* write-only failure (a growing inbox nobody prunes). Absent Op-2, the user's skepticism deepens: you'd have a read that helps occasionally over a pile that only grows.
- **Definitional/Internal-Consistency:** does "the read contributes little to memory" contradict "the read redeems the write-only store"? No — reconciled by enabling-vs-constituting: the read is what makes the *record worth keeping* (enabling), but the record itself is the writes (constituting). Both hold.
- **Strategic:** the honest answer serves the user's real motive — deciding whether pull is worth building. Verdict shape: pull is worth building as *the cheap read that activates the option-memory*, but its value is conditional, and the *stateful* memory needs Op-2 which the doc doesn't specify.

## Phase 4 — Ambiguity Collapse

### Ambiguity A1 — Is the user's confusion a real spec gap or a comprehension miss?

**Confidence:** HIGH.
**Resolution:** it is a **real under-specification** (the doc delivers, and deliberately stops). The user is poking an actual hole.
**Fixed:** the answer opens by validating the confusion, not correcting the user.

### Ambiguity A2 — What is concretely DONE with a surfaced direction?
**Strongest counter (nothing reliable):** the doc punts to "the steering layer," which today is a human — so "what is done" is undefined-by-design.
**Why the counter fails (structural):** even punted, there's a *natural cheap default* the warm session can do without any steering machinery: **absorb-while-warm** (do/incorporate the direction now, since it's in-context), or **note it in the finding**, or **mark it done if addressed**. The punt is about the *choice* (act or not), which doesn't preclude naming the default menu. [S1]
**Confidence:** HIGH.
**Resolution:** the concrete operation is an **offer the warm session judges**: absorb-if-cheap-and-relevant / note-otherwise / mark-done-if-addressed. Not a mandatory "do it now."
**Excluded:** "surfacing forces a derail" — it's an offer, not an interrupt; the session keeps its focus and takes the direction only if cheap+relevant.

### Ambiguity A3 — What is the TRUE benefit (and is it thin)?
**Strongest counter (it's thin/pointless):** the traverse already has a topic, so it'd do its work anyway; surfacing old directions is noise.
**Why the counter fails (structural) — but only partway:** true for directions the session would re-derive; **false** for cross-context directions it would *not* re-notice (the doc's own honest bound, FACT-4) — there, the session does a valuable related thread it otherwise wouldn't, cheaply. So the counter is *correct on the obvious case, wrong on the cross-context case.*
**Confidence:** HIGH.
**Resolution:** **conditional, concentrated benefit** — real on non-obvious cross-context directions; genuinely thin on re-derivable ones. Commit the split; don't oversell. (The user's skepticism is right where it's aimed; it over-reaches if generalized to "always pointless.")

### Ambiguity A4 [LOAD-BEARING] — How does it contribute to traversal memory?
**Strongest counter (the read IS the memory-contribution):** without the Look-Up, the accumulated directions are write-only — the exact failure; so the read is what makes it memory at all.
**Why the counter fails (structural):** the counter proves the read is *necessary for the memory to be useful*, not that the read *is* the memory. Canon's memory = recorded state (visited/selected/outcome) [C2] — that's produced by the *writes* (File accumulates the option-record; mark-done records what was taken). The read consumes that record; it writes nothing. So the read **enables** (activates the record's usefulness) but does not **constitute** (the record is the writes).
**Confidence:** HIGH.
**Resolution:** the reframe that dissolves the confusion — **READ ≠ MEMORY: the read *spends* the memory; the writes *are* the memory.** Pull's contribution to traversal memory is *enabling, not constituting.* The user was looking for the memory-value inside the read; it isn't there because the read is a consumer.
**Depends on this:** the "how is it memory" half is answered by pointing at the write side (File + Op-2 mark-done), not at Look-Up.

### Ambiguity A5 — Where does mark-done belong, and is it the real gap?
**Strongest counter (it's the steering layer's job, already covered by the punt):** the doc punts downstream ops to steering, so mark-done is covered.
**Why the counter fails (structural):** the punt covers the *decision* (act on a direction or not). Mark-done is not a decision — it's a **write to the index recording that a direction is taken**. That's index/routelister housekeeping (the routelister route record already carries a done-column + Priority/Essentiality), not a selection. So the punt does **not** cover it; mark-done falls in a gap between "the Index just delivers" and "the steering layer just chooses." [C3, S1]
**Confidence:** HIGH.
**Resolution:** mark-done is **index-side housekeeping** (belongs with the ODI/routelister layer), and it is **the actual missing piece** — the write that turns a growing inbox into a stateful memory. The field exists; the *habit/step* is unspecified.

## Phase 5 — Conceptual Stabilization

### SV6 — Stabilized Model

**The honest answer, in one shape:** the user's question splits cleanly, and the confusion comes from expecting one thing (memory) to live where another thing (a read) is.

1. **What is done with them?** The warm session gets an **offer**: because it's already in-context on the topic, it can (a) **absorb** the surfaced direction now — do/incorporate it cheaply; (b) **let it inform** the current finding; or (c) **mark it done** if it addresses it. The session judges; nothing is forced. The doc doesn't say this because it deliberately stops at "deliver" and hands the choice to the steering layer — which is a **real under-specification**, so the confusion is well-founded.

2. **What's the true benefit?** **Conditional and concentrated.** It's real and worth it on the **cross-context** directions a session would *not* re-notice on its own (it does a valuable related thread cheaply, while warm). It's genuinely **thin** on directions the session would re-derive anyway. So the skepticism is correct where it's aimed and over-reaches only if generalized to "always pointless."

3. **How is it memory?** **The read is not the memory.** Look-Up is a *read* — it helps the current session; it records nothing. Traversal memory (canon: visited/selected/outcome) is produced by the **writes**: File accumulates the option-record (roads noticed), and **mark-done** records state (roads taken). So pull's contribution to memory is **enabling** (it makes the accumulated record actually consulted, curing the write-only failure) — **not constituting** (the record itself is the writes). *The read spends the memory; the writes are the memory.*

4. **The real gap the question exposes:** the design under-specifies **two** things — the downstream operation (what the session does) and, more importantly, the **mark-done write-back**. Without mark-done the index is a new write-only failure one level up: a to-do pile that only grows. Mark-done is index-side housekeeping (the routelister record already has the done field), and it is the piece that makes the thing a *stateful memory* rather than an inbox.

**Grade of the honest answer:** the user found a real hole. Pull is a cheap, conditionally-valuable read; the "memory" lives on the write side; and the design is missing the mark-done write that would make it memory rather than an ever-growing list.

**Guards:** *Clean-Resolution-Trap* — each A1–A5 carries a structurally-defeated counter (not precedent-dismissed). *Anchor-dominance* — "pull is thin" did NOT halo into "the ODI is worthless" (the index/write side remains the valuable part, per the prior finding); "the user is confused" did NOT halo into "so pull is fine" (the confusion tracks a real gap). *Self-reference* — external anchors throughout (the ODI doc, the SUSTRALL canon, the prior finding, the routelister schema).

**SV1→SV6 delta:** SV1 saw "surfacing specified, use not." SV6 delivers the load-bearing reframe (READ ≠ MEMORY; read spends / writes constitute), the conditional-benefit split, the offer-not-derail operation, and the located gap (mark-done, index-side) — a clear structural shift.

**Highest-value output:** the reframe that dissolves the confusion — *you were looking for the memory in the read; the read spends the memory, the writes are the memory* — plus the honest gap: the design is missing the mark-done write-back that makes it stateful memory.
