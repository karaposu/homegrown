## (c) Candidate verdicts (per-claim adversarial results)

### Claim 1 — Item A trigger-gate: does it actually bound cost (§9)? → **SURVIVES (revised: one scan, not N judgments)**
- *Prosecution:* the trigger ("did context move op X?") is itself a per-op judgment. For cheap ops (MQ1), judging "did it move" may cost ~as much as re-running → the gate saves little and adds overhead.
- *Collision:* the saving is real for the **medium/expensive** ops (MQ3/WHY re-derivation ≫ a "did it move" glance) and marginal for cheap ones — but the fix is framing. The existing spec runs its LAYER 1 self-check as "**one LLM-judgment scanning all modes in one attention**" (`:122`). Frame the trigger the same way: **one "what did the surfaced material actually move?" scan** that gates all on-trigger ops at once, not N separate deliberations. Then the cost is one light pass + re-running only what moved (usually just MQ2+Rephrase) — comfortably within §9.
- **Revision:** state the trigger as a single context-delta scan (mirroring `:122`), not a per-op loop. Cost claim then holds.

### Claim 2 — Item B ownership: warm's, or "sensemaking with a fail-fast flag"? → **SURVIVES (revised: the premise is warm's OBJECT; + honest build-priority)**
- *Prosecution (the sharp one):* the same fail-fast value could come from running sensemaking first-and-fast with a premise-check — so "conflict-detection in warm" may be mere placement.
- *Collision:* the stronger argument isn't timing, it's **object-ownership**. The "premise" that conflict-detection checks **is the re-anchored request — warm's own output.** Checking whether the framing survives contact with reality is checking **warm's product against reality**; sensemaking *consumes* the frame (takes it as given) and *builds a model*. A discipline should validate its **own** output's premise, not delegate it to a downstream consumer that is biased to reconcile. So it's warm's by object, not just by timing. (Timing — earliest post-surfacing point — is a secondary reason.)
- *But honest sizing:* premise-conflicts are **rare**, so B is a **low-frequency safety-net**, whereas A fires **every** warm pass. → **build-priority A ≫ B** (see backstop-iii). The distinctness holds; the priority is asymmetric.

### Claim 3 — Item B canon-consistency: is every discipline-side step emit-only? → **SURVIVES (clarified: grade ≠ adjudicate)**
- *Verification (who-acts):* detect = identify-output (`:132` DNA); flag+payload = verdict-output (`:230`); surface/ask/block = runner. All emit; no discipline-side pause/halt. ✓ (NOT-List#2 `:133` / Stance#3 `:117` preserved.)
- *One sharp sub-prosecution:* the **severity judgment** (resolvable vs severe) — is that adjudication (NOT-List#1 `:132`)? **No:** grading a conflict's *severity* is the same kind of self-grading the verdict system already does (MED vs HIGH). It does **not** adjudicate the *content* (it never decides request-vs-reality is "right"). **Clarification for the spec:** warm **grades the conflict's severity**; it does **not adjudicate the conflict** — keep that line explicit so the build doesn't drift into "warm decides who's right."

### Claim 4 — the context-symmetry: real unification or cute frame? → **SURVIVES (sized: organizing frame, not a load-bearing claim)**

The inversions map to commit/[A]/[B]. Real.
- *But:* the symmetry **organizes**, it doesn't **do work** — the work is the re-run table + the conflict mechanism. **Sized as a presentational/organizing frame**, consistent with innovation's own honest sizing of the assembly-lens. Don't oversell it as a discovery; present it as the lens that makes A and B legible as one move. (A ⊥ B independence confirmed intact — the frame explains, doesn't couple.)

## (d) ★Backstop — what the design MISSES

- **(i) A's trigger = one scan** (folded into Claim 1) — the innovation's per-op framing invited a cost objection; fixed by the single-scan framing.
- **(ii) Who formulates the clarifying question?** The design says warm emits a "question payload" but doesn't say who *writes* it. Answer: **warm formulates** it (it detected the conflict, it knows the gap), the **runner asks** it. Formulating = identify + phrase (emit); consistent. **Amendment:** state explicitly — warm *formulates* the question as flag-payload; the runner *poses* it.
- **(iii) ★BUILD-PRIORITY: A ≫ B.** The design treats A and B as co-equal outputs; they are not, for *build priority*. **Item A fires every warm pass** (the core operation-set — high-frequency value); **Item B fires rarely** (premise-conflicts are uncommon — a safety-net). So if anything is built: **A first** (correct §4 + the re-run principle — improves every run), **B second** (the rare-but-catastrophic safety-net). The Next Actions must **order** them, not list them flat.
- **(iv) ★The conflict-flag OVERLOADS the verdict.** Reusing `HIGH-FLAG` (currently "very confident the flagged **operational** condition exists," `:245`) for a **content-conflict** means a consumer can't tell an *operational* flag from a *content-conflict* flag. Since Item B's severe rung wants the runner to **selectively block** (content-conflict → maybe block; operational → just display), the runner **must** be able to tell them apart. **Amendment:** the conflict-flag needs a **TYPE-discriminator** (a flag-type tag `content-conflict`, or a distinct verdict) so the runner can apply the block-policy selectively. The innovation's "reuse the FLAG action" was right about the *action* but under-specified the *discriminator*.
- **(v) Consistency note (not a miss):** the on-trigger judgment (A) is another LLM-judgment edge — consistent with the spec's "determinism on judgment-call edges intentionally not committed" (`:124`). Fits the existing stance; no problem.
