### Candidate P2 — Dual-Mode Essence

#### Prosecution

**Dimension-level (D6, D10):** Dual-mode is more complex than single-mode essence. Adds cognitive load.

**Specific failure-case scenario:** LLM struggles to detect "warm" vs "cold" context reliably; dispatch is brittle; same task in same session produces different outputs depending on perceived warmth.

**User-perspective objection:** User wanted ONE solution (3-tier). Dual-mode keeps both 20-02's mode and adds warm-context mode — feels like compromise.

**Specification-gap probe:** What counts as "warm enough" vs "cold"? threshold unclear at Bootstrap.

#### Defense

**Core strength (D5 robustness):** Dual-mode reflects the actual structural truth — cold-context cases DO occur (fresh sessions, unrelated tasks); warm-context cases DO occur (continuing threads, project-rooted work); both need handling. Single-mode is brittle in one direction.

**Counter to specification-gap:** LLM-judgment-level dispatch is consistent with how other operations use context. MQ2 + MQ3 already use warm context per 20-02's anti-fetching re-interpretation; they judge warm-vs-cold per-invocation. Same pattern applies. At Mature Operation (~30+ invocations), empirical patterns may emerge for explicit threshold guidance.

**Counter to user-perspective:** User's 3-tier proposal would ALSO need cold-fallback (immediate-tier-only when no warm context); the dual-mode pattern is structurally inherent to any context-using operation, not specific to this verdict.

**D6 (elegance):** Dual-mode is minimum-complexity solution that handles both cases; alternatives (single-mode) sacrifice one case.

**D10 (lightness):** Dispatch is LLM-judgment-level, not sub-machinery. No additional operations or pipeline complexity.

#### Collision

Defense survives. Sub-finding: §2.4 worked example should explicitly contrast cold-context output (hypothetical small/big) vs warm-context output (concrete small/big) so the dual-mode distinction is concrete for readers.
